# Digest 003 - ECS Architecture & Entity Interaction API

## 1. Purpose
Defines entities as pure data (component maps) created from declarative prototypes, typed system functions operating on them, a high-reuse `TaskQueue` component (priority + interruption + CancellationToken), and a two-layer async/await model where promises are runtime-only and resolve from tick-driven serialized state machines.

## 2. Module layout / public API (as stated)
Implied: `ecs/prototype` (EntityPrototype registry + instantiate), `ecs/entity` (Entity, add/remove component, version), `ecs/components` (Component defs), `ecs/taskqueue` (TaskQueue, Task, CancellationToken), `ecs/async` (AsyncOperation state machines, promise bridge), system function families (inventory 005, movement, trade).
- Prototype: `{ id: "Citizen", components: ["Position","Inventory","Job"] }` + default component values (exact definer function e.g. `definePrototype` NOT named).
- Entity JSON: `{ id: int, prototype: string, components: { Name: {...} } }`; `version` runtime-only, 0 on load, +1 on every component add/remove (names of add/remove fns not given).
- Typed fns: `getBalance(entity)`, `store(entity, material, quantity)` (spec 005); enforced via TS type predicates/branded types; no methods on entities; O(1) component presence check.
- Component `TaskQueue`: stores pending tasks, current task, execution history; ops: enqueue, dequeue, prioritize, interrupt (names generic).
- `Task`: id, priority, status (pending|executing|completed), serialized checkpoint; promise runtime-only.
- `CancellationToken`: category `graceful | ungraceful` (+ reason string per 006 FR-010, e.g. "entity_deleted","interrupted_by_priority").
- `AsyncOperation`: tick-level state machine serialized in task record; reactive (registers once, evaluated only on relevant game events).
- Async behavior fns: `await walkTo(entity, targetCell)`, `await craft(entity, recipe)`, `await purchase(entity, seller, item, count, price)`.
- Errors: descriptive rejection e.g. `InsufficientFundsError` (fail-fast when provably unachievable).

## 3. Functional requirements
- FR-001 declarative prototype syntax (id + component list).
- FR-002 instantiate entity from prototype with default component values.
- FR-003 instances independent (no shared mutable state).
- FR-004 typed system functions on entity data; behavior in functions not entities.
- FR-005 compile-time enforcement of required components.
- FR-006 TaskQueue component: enqueue/dequeue/prioritize/interrupt.
- FR-007 highest priority executes first each tick.
- FR-008 interruption cancels remaining tasks, leaves consistent state.
- FR-009 async/await syntax, promises resolve by tick progression not wall time; tick state machine resolves them.
- FR-010 walkTo resolves when pathfinding state machine reaches target cell.
- FR-011 purchase resolves after entity walks to seller and exchanges inventory/money over multiple ticks.
- FR-012 sequential awaits run in order (task queue enforces ordering) w/o explicit state machines in behavior code.
- FR-013 high-reuse system function families (inventory, movement, trade) composable.
- FR-014 serialize all entity state incl. task queue and in-progress async phase.
- FR-015 deserialize + resume async ops at saved phase; promises never serialized; scripts resume from task checkpoints.
- FR-016 headless parity.
- FR-017 components addable/removable at runtime; version increments; version not serialized.
Rules: tasks run to first `await` per tick; one task at a time per entity; concurrency only across entities; delete entity => ungraceful token cancels tasks, external awaits reject; required component removed mid-op => op rejects (no loop crash); error in system fn propagates leaving entity consistent; SC-012 complex flows <50 lines; SC-005 interrupt completes within one tick.

## 4. Dependencies
Consumes: 001 tick; 004 pathfinding/Position (walkTo); 005 inventory fns; 010 event bus (reactive wake, `waitFor`); 011 PRNG; 006 serialization; 012 (movement/ re-eval). Provides: Entity/Component/Prototype model to ALL specs; TaskQueue to jobs/behaviors; entity version to 002 caches.

## 5. Ambiguities / contradictions / blockers
- BLOCKER (core): behaviors are written as JS `async` functions, yet "native promises are never serialized" and scripts "resume from serialized task checkpoints". JS cannot resume an async function mid-await after reload. Spec never defines checkpoint format, how scripts are re-entered (replay with memoized step results? explicit step list/state-machine DSL? behavior scripts registry keyed by task type?). Needs a design decision (e.g., behaviors as resumable step interpreters; await only over serialized ops).
- "Each await in a sequence is queued as a separate task" vs "task runs to first await per tick" vs FR-012: unclear whether a script is ONE task with N awaited AsyncOperations or N tasks; how a not-yet-executed `await` becomes a queued task before code runs to reach it.
- Task priority vs sequencing: highest priority first conflicts with strict await ordering (do later awaits of low-priority script get preempted?). Interrupt scenario says "current task completes its current step, queued tasks cleared" - unclear vs graceful/ungraceful cancellation semantics and which token category interruption uses.
- OPEN question: changing priority of an executing task (finish vs interrupt) undecided.
- Task statuses lack cancelled/failed/rejected; history retention/cap undefined (unbounded growth in saves); what "completed tasks inspectable" stores.
- Prototype serialization (US1 AC4 "prototype serialized to JSON") contradicts 006: prototypes are NOT in save, loaded separately at startup. Prototype/component registry API (component schema, defaults, factory) not specified; how default values defined per component (schema? Zod?).
- Reactive wake-up needs named events/hooks (movement, inventory change) from 010 not yet defined here; interplay with 005 tick-boundary events and sync visibility.
- Branded-type enforcement vs runtime: how does a runtime-added component (FR-017) type narrow? Type guard `hasComponent(entity,'Inventory')` shape not given.
- Entity deletion API/ID allocation (`nextEntityId` counter) not here; 006 omits it.
- Component data must be JSON-only (no funcs); validation not specified. Entity "state" besides components undefined.
- Error class catalogue (InsufficientFundsError etc.) lives in 005; unreachable-path error not named.
- "Entities diverging" synchronization claim hand-wavy; no two-entity transactional rule for purchase (partial failure rollback? atomic exchange).

## 6. Acceptance scenarios / tests
- Prototype with 3 components -> entity has defaults; multiple instances independent; 5+ prototypes human-readable; deterministic instantiation.
- Compile-time: getBalance(entityWithoutInventory) is a TS error (type test via tsd/expect-type); runtime O(1) has-component.
- TaskQueue: priorities [1,10,5] execute [10,5,1]; interrupt mid-task -> queue cleared, clean state within 1 tick; reprioritize preserves state; history inspectable.
- Async: walkTo 5 cells resolves ~5 ticks; craft resolves after duration ticks with outputs; composed walk/purchase/walk sequential; concurrent entities deterministic; save mid-op + load resumes and resolves at same tick; nested awaits no deadlock.
- Edge: component removed mid-op => rejection; entity deleted => rejects with ungraceful cancel; system fn throw leaves consistent state.
- Serialization: bit-identical round trip; version resets to 0; no opaque fields; two instances identical after N ticks; headless == browser.

## 7. Size: XL (the resumable async/task model is the hardest piece in the whole engine; prototype/type machinery is M).
