# Digest 002 - Entity Access & Query Helpers

## 1. Purpose
Framework-level, index-free (full-scan) query API over the entity collection: by component, by dotted property path (equality/range/AND), and by relationship, plus reusable domain query-helper classes and a benchmark suite. Results deterministic in insertion order.

## 2. Module layout / public API (as stated)
Implied: `query/` (core query functions, location unspecified: on GameState/engine?), `query/helpers/` (`CitizenQueries`, `FactionQueries`, `ResourceQueries`), `bench/` (benchmark suite + JSON report).
- `getEntitiesByComponent(componentType: string): Entity[]`
- `getEntitiesByProperty('Component.field', value | { min?: number, max?: number }): Entity[]` (dot path, component-scoped; id/prototype NOT queryable)
- `getEntitiesByProperties({ 'Citizen.currentJob': 'farm.sow', 'Citizen.status': 'active' }): Entity[]` (AND)
- `getRelatedEntities(entity, relationshipName: string): Entity[]` (e.g. `(faction,"members")`, derived by scanning `Citizen.factions`)
- `getRelatedEntity(entity, relationshipName): Entity | null` (e.g. `(citizen,"currentJob")`)
- Helper classes: `CitizenQueries.getActiveCitizens()`, `.getCitizensInFaction(factionId)`; chainable `.filter(...)`; need 5+ helpers in tests.
- `BenchmarkResult { entityCount, queryType, executionTimeMs, memoryUsage? }`; JSON benchmark report; baseline compare with >10% regression alert.
- Entity JSON: `{ id: int, prototype, components: { Name: {...} } }`. Multi-value fields (`Citizen.factions` = list of faction entity IDs) must be matchable.

## 3. Functional requirements
- FR-001 getEntitiesByComponent.
- FR-002 getEntitiesByProperty equality, dot-notation path.
- FR-003 range operator {min,max} for numeric props.
- FR-004 getEntitiesByProperties AND logic, same path syntax.
- FR-005 getRelatedEntities; THROW if a related id is deleted (dangling = integrity bug).
- FR-006 getRelatedEntity single or null; throw if referenced entity deleted.
- FR-006a Owners of reference fields must clear them when target destroyed (e.g. faction leaderId -> null, standings removed; spec 021).
- FR-007 deterministic, insertion order (order added to game state) is canonical.
- FR-008 identical behavior on live vs deserialized state.
- FR-009 reusable helper classes (Citizen/Faction/ResourceQueries).
- FR-010 benchmark tests 100 / 1000 / 10000+ entities.
- FR-011 no dependency on renderer/UI.
- FR-012 helpers composable/chainable.
- FR-013 results are live views; caller must not add/remove entities during iteration (undefined if so); no indexing/caches in framework.
Perf: SC-001 component query 10k entities <5ms; SC-002 single prop <10ms; SC-003 3+ filters <15ms; SC-004 relationship query <5ms (max depth 5); SC-006 +-10% variance across envs; SC-009 CI detects >10% regression; SC-010 no leak over 100k+ iterations.

## 4. Dependencies
Consumes: 003 (Entity/Component model, prototype ids), 006 (entity JSON shape, entity array order = insertion order after load). Provides: query layer for every system (005 permission/faction lookups, 021 factions, 004 occupants maybe). Mentions spec 021 (Faction entities; members derived).

## 5. Ambiguities / contradictions / gaps
- Host of the API unspecified (free functions? GameState/engine methods? 007 `getEntities()` only). How the functions get the entity collection (parameter vs ambient state).
- OPEN: `getRelatedEntity` when multiple targets: first match vs throw. Must be decided.
- Relationship definitions: no registry/format maps name ("members", "currentJob") to component field, direction, cardinality, or inverse derivation. Needed to implement FR-005/006.
- Type conflict: `getEntitiesByProperty('Citizen.currentJob','farm.sow')` treats currentJob as a string (task/job type) while `getRelatedEntity(citizen,"currentJob")` returns a job ENTITY - same name, different type.
- "Live view" (FR-013/edge case) vs Assumption "result is a new array (modifying it doesn't affect collection)" - clarify: new array of live entity refs.
- Range inclusivity, non-numeric field with range, missing component/field on some entities (skip vs throw), null handling, equality semantics for object/array values; array-field membership semantic for `Citizen.factions` ("contains X") and AND/OR across values (clarification mentions "X AND/OR Y") not specified in API.
- Insertion order after entity removal and after load (relies on 006 entities array order being preserved); ID reuse not allowed (006 says never GC) OK.
- Throwing on dangling refs mid-query contradicts scenario 3 ("circular relationship traversal"): need traversal API / visited set; "relationship depth max 5" has no API for depth/multi-hop.
- Benchmark: CI regression >10% vs +-10% environment variance -> flaky; "reference hardware" undefined; memory usage Node-only; baseline storage location/format undefined; benchmarks should be separate from unit test run.
- "Find nearest entities" helper (US4) needs spatial query not defined here (004).
- Error classes for dangling/unknown component not named.

## 6. Acceptance scenarios / tests
- 50 entities (30 Citizen) -> 30; empty collection -> []; unknown component -> []; newly added entity included next query; headless parity.
- 200 citizens property equality; range {min:-50,max:0}; multi-prop AND; unmatched value -> []; deterministic after save/load.
- Faction w/ 50 members via `Citizen.factions` -> getRelatedEntities 50; getRelatedEntity job; circular chain terminates; deleted target -> throws; relationships rebuilt after load.
- 5+ helpers, composition, refactor locality.
- Benchmarks at 100/1000/10000+; JSON report fields; regression compare; memory stable 100k iterations; insertion-order determinism; result array mutation does not affect collection.
