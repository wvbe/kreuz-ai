# Digest 012 - A* Pathfinding

## 1. Purpose
Deterministic integer-cost A* over the spec-004 cell adjacency graph (4-connected square, Delaunay dual voronoi), with cross-map routing via Transition entities, path cache/invalidation, terrain costs and reachability queries.

## 2. Module/API (as stated)
Spec states NO function signatures. Named concepts only:
- `PathNode { cellIndex, cost, heuristic, parent }`; `Path` = sequence of discrete cells/regions (empty if same position, ALSO "empty if no path" per Key Entities - see 5); `Map` (004); `Transition` = entity with `Position` and `Transition` components (per 006) joining maps; `MovementCost` integer cost per terrain type / entity state.
- Positions: `{ cellIndex }` on all grids; square maps also accept `{ cellX, cellY }`.
- Needed (implied) queries: findPath(start, target[, entity/movement type]) -> Path | "no path"; reachable(from[, map]) -> set (FR-010: "what is reachable from X"); path validation/invalidation (FR-006); config of terrain costs (FR-009; terrain registry spec 022 holds traversability+cost).
- No commands or events defined.

## 3. Functional requirements
- FR-001 A* on adjacency graph with integer edge costs; heuristic admissible: Manhattan on square; voronoi = centroid straight-line distance scaled to integer and rounded DOWN; both multiplied by the minimum per-step terrain cost (Assumptions).
- FR-002 Shortest path avoiding non-traversable cells (terrain traversability, wall entities, door entities by state).
- FR-003 Only adjacency edges: orthogonal on square (no diagonal), Delaunay neighbours on voronoi; integer costs.
- FR-004 Return "no path exists" when target unreachable.
- FR-005 Cross-map navigation through exit/entrance connection points (Transition entities).
- FR-006 Cache/validate paths; detect obstacle-invalidated cached paths.
- FR-007 Concurrent requests without race conditions (single-threaded sync => deterministic ordering).
- FR-008 <100ms typical room-size map.
- FR-009 Configurable terrain costs per tile type.
- FR-010 Reachability query.
- Assumptions/rules: entities never block cells (multiple per cell; only terrain/wall/door/furniture-that-blocks); no flying unless flagged; static costs within a tick; deterministic tie-break "using the game's seeded PRNG (spec 004)"; open/closed sets in memory; target outside bounds => "no path" (invalid position) without crash.

## 4. Dependencies
Consumes: 004 (maps, adjacency, cell indices, wall/door entities, bounds), 022 (terrain registry: traversability + integer cost), 006 (Transition entity serialization), 011 (tie-break PRNG), 001 (tick sync). Provides: paths/reachability to 009 (connectivity validation), 013 (movement), 014 (gathering), 003 (move tasks), 015 (nothing direct), hauling 018.

## 5. Ambiguities / contradictions / blockers
- No API shape at all: path return type (cells list vs steps, include start?), "no path" representation (null vs `{found:false}` vs error), entity/movement-type parameter (US4.2 "entity with different movement types"), cache key/invalidation API, replan events. Needs full design before implementation.
- CONTRADICTION: US1.4 "same position -> returns empty path (already at target)" vs Key Entity Path "empty if no path exists" => empty path ambiguous. Use explicit result discriminator.
- Tie-breaking: "seeded PRNG" (cited as spec 004; PRNG is spec 011) vs SC-001 "identical input produces identical path": a PRNG-based tie-break makes output depend on PRNG stream position (consumption order, caching, concurrent requests) and on whether a search re-runs - not a pure function of input. Also each search consuming PRNG values perturbs global sequence for save/load. Recommend deterministic tie-break (lowest cellIndex / f then h then index) or per-search seed from (derived stream "pathfinding", request id). 011 says pathfinding receives a derived PRNG.
- Open questions: start cell blocked (stuck vs allowed to path out); node limit for long paths; voronoi heuristic scaling exact formula; cost units (is 1 = base step? min step cost is tracked per map?).
- US3.2 moving target "if requested" - no API; US3.1 "detects it and recomputes or alerts entity" - mechanism (event? polling?) undefined; no event names (e.g., `path.invalidated`).
- Cross-map: cost of Transition traversal, bidirectional?, which cell coordinates, search graph (hierarchical map-graph vs flattened); optimal route across maps among alternatives; transitions blocked by door state; SC-003 <=50ms overhead.
- Door entities by state: closed door traversable? (spec 004 decides; 015 says doors count as enclosure) - confirm closed doors are passable for pathing (otherwise rooms unreachable).
- Terrain with `impassable` vs cost; per-entity traversal modifiers (flying) mentioned but out of scope; "swimming".
- Performance targets conflict slightly: SC-002 100ms for 50x50 w/20% obstacles vs FR-008 "typical room"; fine.
- Reachability query return: set of cellIndex, with costs? bounded by max cost? 009 also needs component-connectivity (flood fill) cheaply (<50ms validate).

## 6. Tests to derive
US1: (5,5)->(15,15) empty square length = 20 (Manhattan, 4-connected); wall at (6,5) detour; enclosed start -> no path/valid; start==target -> zero-length path.
US2: A->B via exit(20,10)/entrance(0,10); unconnected maps -> "no path"; A->C through B; multiple routes -> minimal cost.
US3: obstacle appears on cached path -> invalidated/replanned (<50ms SC-007); target moves recompute; many requests each valid.
US4: road cost 1 vs grass 2 preferred; per-movement-type cost; impassable never entered.
Edge: out-of-bounds target no crash; unreachable island; voronoi map (centroid heuristic admissible - property test comparing against Dijkstra for optimality, SC-001); determinism (same input same path, repeated runs); 50x50 w/20% obstacles <100ms; reachability sets.

## 7. Size: M (A* is small; cross-map graph, cache invalidation, voronoi heuristic, and API design push it up).
