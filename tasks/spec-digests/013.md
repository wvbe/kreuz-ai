# Digest 013 - Entity AI Behavior Architecture

## 1. Purpose
Hybrid Behavior Tree (structure) + Utility AI (scoring) decision system driven by needs, mood, relationships, skills/traits (no occupation component), and wealth, loaded as JSON DSL/plugins at bootstrap (immutable).
Deterministic action selection (<5ms/entity), with role-derived need priorities, mood-scaled risk, decaying relationship memory.

## 2. Module/API (as stated)
- Components/data: `NeedState` (hunger, rest, safety, social), `MoodState` (0-100 + recent influences), `Relationship` (affinity/trust, history, faction/family), `DecisionContext` (needs, mood, relationships, wealth), `Role Profile` (DERIVED, not a component), `BehaviorTree`, `BehaviorNode` (returns success/failure/running), `UtilityScore`, `BehaviorDSL` (JSON schema of spec 022 FR-014: node types `selector` | `sequence` | `condition` | `action`; condition/action reference engine-registered handlers by name), `BehaviorPlugin`, `DecisionFactor` (plugin interface for weighting).
- Tree depth <= 5. Example DSL tree: selector[ sequence[condition `is_starving`, action `beg`], action `work` ]; sequence [Check Hunger -> Find Food -> Eat].
- Event: `need.item.consumed { entityId, needId, materialId, quantity }` (FR-023).
- Config referenced elsewhere: need registry (022) per-need critical thresholds + default priority order; `needDecayMultiplier` (027 FR-015); example priority orders: Guard Safety>Rest>Hunger>Social; Merchant Social/Trust>Hunger>Rest>Safety; Farmer Hunger>Rest>Safety>Social.
- Numeric rules: mood risk-success mapping linear: p(mood=10)=20%, p(90)=80%, p(50)=50% => p = 20 + (mood-10)*60/80 (%), extremes undefined. Critical need threshold example in US1.4: all needs > 30% = non-critical (registry decides). Wealth example thresholds: >500 coins wealthy, <50 poor. Relationship decay examples: effect fades "50+ ticks"; "100+ ticks" old damage offset by gift. SC-005: redirect within 1-3 ticks. Plugin overhead <=2ms; AI state <1KB per entity.
- No commands; no function signatures; no JSON shape for Relationship/NeedState.

## 3. Functional requirements
- FR-001 Needs system, at least hunger, rest, safety, social.
- FR-002 Needs decay over time (scaled by `needDecayMultiplier`; thresholds/restoration unscaled) and are satisfied by specific actions: Hunger<-consume `food` items; Rest<-sleep in Bed locations (prefer own dwelling beds, never another household's, 029 FR-017); Safety<-proximity to Guards/safe zones; Social<-conversation actions. Eaten `food` recorded for household food variety (029 FR-018).
- FR-003 Critical-need priority by personality (prototype + traits), defaults/thresholds from need registry (022).
- FR-004 Mood 0-100 from need satisfaction, successes, relationships.
- FR-005 Mood affects decisions: mood 10 => risky action 20% success; mood 90 => 80%.
- FR-006 Relationships: affinity (trust), history (conflicts, gifts, time since interaction), faction/family alignment.
- FR-007 Relationship changes persist; history tracks contract-breaking, gifts, family membership, time decay (recent weighted higher).
- FR-008 Skills/traits (020) + prototype determine goals and skill bonuses (no occupation component).
- FR-009 Wealth constrains access to activities.
- FR-010 Wealth influences decisions (poor survive, rich luxury).
- FR-011 Unified decision architecture combining needs, mood, relationships, skills/traits, wealth.
- FR-012 Hybrid model: BT structure + Utility scoring.
- FR-013 Node types selector/sequence/condition/action; handlers by name, unknown = load validation error; depth <= 5.
- FR-014 Utility AI weights competing behaviors, picks highest score.
- FR-015 DSL = JSON node schema of 022 FR-014.
- FR-016 Behavior plugins loaded at bootstrap, immutable; plugin and behavior names globally unique; duplicate = load failure.
- FR-017 New behaviors/factors via DSL or plugins, no core change.
- FR-018 Minimal in-memory AI state (current behavior, active needs, recent mood, recent interactions).
- FR-019 Evaluate and select next action <5ms per entity.
- FR-020 50+ entities concurrently without degradation.
- FR-021 Entities can switch trees/strategies at runtime (among bootstrap-loaded ones).
- FR-022 Deterministic: same state => same action.
- FR-023 Emit `need.item.consumed` on need-satisfying consumption (for ProductionLedger, 025 FR-012).
- Rules from edge cases/clarifications: cycles in behavior references rejected at load; zero skill still can attempt (success reflects 0); faction standing is baseline affinity offset = average over shared faction pairs (spec 021), personal history applied on top; relationships asymmetric; mood recovers toward neutral; needs decay linearly; entity commits to action once started (discrete ticks); plan 3-5 steps; role stable until skills/traits change.

## 5. Ambiguities / contradictions / blockers
- Units: mood 0-100 "%" vs Constitution fixed-point milli-units (is mood 0..100000?); needs "%" (30%) likewise; probabilities 20/50/80 need integer representation; success roll uses which PRNG stream (derived name unspecified) - but FR-022 "same state => same action" ignoring roll order. Who defines "risky action" and its base success probability? (US2: "80% success probability" at mood 90 is the action's resolved probability, not a modifier of a base - formula for actions with own base risk absent.)
- Extremes: mood 0/100 and outside 10-90 (clamp vs extrapolate: linear extrapolation gives -?%). Open questions flagged: all-bad options, sudden relationship loss (friend dies), impossible goals.
- Utility scoring formula entirely absent (weights, normalisation, factor interface `DecisionFactor` signature, tie-break); how BT interacts with utility (utility chooses which tree/root behavior? chooses among selector children?); "running" status persistence/serialization across save; link to task queue (003) checkpoints.
- FR-018 "in memory" vs Constitution II/SC-006: relationships must persist across saves; mood/needs/AI state serialization and shape unspecified (mood/need are components -> JSON); "recent interactions" cap size under 1KB.
- Relationship numbers: affinity range, event magnitudes, decay function/rate ("50+ ticks", "100+ ticks" illustrative), gift offset amount, thresholds "high affinity 80%+", "affinity drops 30%". Data-driven constants needed.
- Wealth: "treasure" > 500 / < 50 "coins" hard-coded in scenarios vs data config; where wealth is read (inventory currency in which currency material?) and household wealth (029).
- Season/harvest (US4.1) acknowledged open - no calendar spec; farmer behavior untestable.
- Guard role detection: "Guard", "Merchant" labels derived from skills/traits/prototype - derivation algorithm unspecified yet needed for need-priority (FR-003) and tests (US1 requires a Guard entity: use prototype/trait fixture).
- Safety need satisfied "by proximity to Guards/safe zones" - requires a zone effect (015) or guard entity query; no spec link. Social via "conversation actions": action handler registry not enumerated (handler names such as `is_starving`, `beg`, `work` are illustrative; the list of engine handlers belongs to 022/other specs).
- Performance numbers inconsistent: <5ms per entity vs 50ms total for 50+ entities (=1ms/entity) vs plugin 2ms overhead.
- Event of FR-023 payload `needId` etc. consistent; no other events (mood changed, relationship changed) defined although other specs (028 chronicle) may need them.
- Duplicate-behavior-names between plugins (load error) vs content packs merging order unspecified.
