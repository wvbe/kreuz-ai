# Digest 005 - Inventory System

## 1. Purpose
`Inventory` component + synchronous, atomic, typed system functions for stacked slots, weight, perishables (per-stack fixed-point timers), equipment slots, money-as-material, transfers and permission rules. Events are emitted at tick boundary; queries see new state immediately.

## 2. Module layout / public API (as stated)
Implied: `inventory/components` (Inventory, Equipment), `inventory/ops` (store/retrieve/...), `inventory/materials` (Material registry, immutable after bootstrap), `inventory/perish` (per-tick decay system), `inventory/errors`, `inventory/permissions`.
- Functions (all sync, non-awaitable, take entity data first): `store(entity, material, qty)`, `retrieve(entity, material, qty)` (returns removed items), `storeUpTo(entity, material, qty) -> { stored, remainder }`, `canStore(entity, material, qty) -> { fits, maxFittable }`, `canRetrieve(entity, material, qty) -> { available, quantity }`, `availableSlots(entity)`, `availableWeight(entity)`, `getTotal(entity, material)` (sum across stacks; mentioned, includes equipment in "all items" query), `transfer(source, destination, material, qty)`, `getBalance(entity)`, `credit(entity, amount)`, `debit(entity, amount)`, `equip(entity, material, slotName)`, `unequip(entity, slotName)`.
- Types: `Material { id (lowercase snake_case string), name (display), stackLimit, weight? (non-neg int), perishability? (ticks) }`; `InventorySlot { materialId, quantity, [remainingTime (fixed ×1000 ticks), decayRate (fixed, 1000=normal)] }`; `EquipmentSlot { name, typeRestriction, item|null }`; `PermissionRule { type: PermissionType(Grant|Deny), target: EntityId|FactionId|RoleType, operation: InventoryOperation(Store|Retrieve|Transfer|Equip) }`; Inventory has slot count, `InventorySlot[]`, owner entity id, optional weight limit, `PermissionRule[]`.
- Errors: `InventoryFullError`, `InsufficientItemsError`, `InsufficientFundsError`, `DestinationFullError`, `WeightLimitExceededError`, `EquipmentSlotIncompatibleError`, `AccessDeniedError`, `UnknownMaterialError`.
- Events (tick boundary): `inventory.item.stored|retrieved|transferred|expired|equipped|unequipped` (payload shapes not given); consumers use `event.waitFor()`.
- Constants: money stack limit 1000 (specs 019/022); wood 50, cheese 20 examples; 48h = 576 ticks; fixed-point decay 1000 = 1 tick/tick.

## 3. Functional requirements
- FR-001 Inventory component attachable to any entity. FR-001a all ops sync, return immediately.
- FR-002 configurable slot count per instance.
- FR-003 per-material stack limits; FR-003a materials by stable string id (not name).
- FR-004 fill existing partial stacks before new slot.
- FR-005 reclaim slot at qty 0.
- FR-006 store (all-or-nothing). FR-007 retrieve.
- FR-008 over-capacity store => InventoryFullError, unchanged. FR-009 over-retrieve => InsufficientItemsError, unchanged.
- FR-010 canStore (no mutation). FR-011 canRetrieve.
- FR-012 getBalance/credit/debit over money material.
- FR-013 debit insufficient => InsufficientFundsError; balance never negative.
- FR-014 atomic transfer (source sufficient, destination fits, else no partial state).
- FR-015 storeUpTo returns {stored,remainder}, never errors on capacity.
- FR-016 per-material optional integer/fixed-point weight.
- FR-017 per-inventory optional weight limit => WeightLimitExceededError on store/transfer.
- FR-018 availableWeight.
- FR-019 optional per-material perishability duration.
- FR-020 per-stack remaining time = fixed-point ticks (×1000, init = duration×1000), decremented each tick by stack decay rate (1000 normal; pantry multiplier spec 018); difficulty `decayMultiplier` (027 FR-015) applied AFTER container/zone multiplier, rounding per 027 FR-014.
- FR-020a merge on store into partial perishable stack: newRemaining = floor((oldQty*oldRem + newQty*newRem)/(oldQty+newQty)).
- FR-021 expired stack (remaining hits 0) removed whole; emit `inventory.item.expired` at tick boundary.
- FR-021a emit stored/retrieved/transferred at tick boundary.
- FR-022 named equipment slots, one item each. FR-023 type restriction => EquipmentSlotIncompatibleError. FR-024 atomic equip/unequip (swap on occupied slot).
- FR-025 owner id + permission rules `{type,target,operation}`; unauthorized => AccessDeniedError. FR-025a checked at call time (no cache), default open, first matching rule wins.
- FR-026 serialize all (slots, material ids, quantities, stack limits, remaining time, decay rate, weight, equipment, ownership, rules). FR-026a store ids not names. FR-027 deserialize identically.
- FR-028 headless parity. FR-029 state immediately visible to sync queries in same tick.
Edge rules: stack limit change => existing stacks valid; slot-limit reduction keeps contents; unregistered material => UnknownMaterialError; unequip with full inventory => InventoryFullError (item stays equipped); no partial expiry; equipped items recompute weight on query; transfer location-agnostic; deletion of inventory-holding entity handled by caller.
Perf: SC-001 ops <1ms (100 slots, 10k items); SC-009 stored+remainder==qty; SC-010 expiry within 1 tick.

## 4. Dependencies
Consumes: 003 (entity/component/typed fns), 001 (ticks), 010 event bus (`waitFor`, tick-boundary delivery), 019 (currency material), 022 (registries, money stack), 018 (pantry decay multiplier), 021 (factions for permission target), 027 (decayMultiplier), 006 (serialization), 011 PRNG (mentioned for slot order). Provides: store/retrieve/transfer/money to trade, production, crafting, taxes.

## 5. Ambiguities / contradictions / blockers
- ERROR in spec example: US3 AC1 `canStore(entity,"wood",60)` with "2 open slots, wood 8/50, limit 50" => existing stack room 42 + 2*50 = 142 (would FIT); stated `maxFittable: 52` and `fits:false` don't compute (42+50=92 even with 1 slot). Example must be fixed before it becomes a test.
- BLOCKER: permission checks require an ACTOR but no function takes an actor (`store(entity, ...)`, `transfer(source,destination,...)` only). Need `actor` param/context. Also which inventory's rule applies in transfer (source Retrieve vs dest Store vs Transfer op?), what happens when rules exist and none match (allow? deny?), how `RoleType`/FactionId targets resolve (needs 002 queries/021), "Deny precedence when explicitly ordered" is just first-match.
- Unit/scale conflict: constitution/006 FR-014 says ×1000 fixed-point unless better unit; quantities plain integers (ok), but weight uses "tenths" in US7 ("0.1 as integer tenths") vs generic fixed-point; weight scale undefined (Stone 5, Feather 1 tenth => limit 50 means 500 tenths?). Perish remaining ×1000 ticks vs Material duration "game ticks" (conversion x1000 at store).
- Money: stack limit 1000 per slot => balance capped by slot count (1,000,000 needs 1000 slots); credit can throw InventoryFullError; money quantities integer units vs ×1000 milli? Is `credit(100)` = 100 units? Also weight of money.
- Serialized per-slot `stackLimit` (FR-026, US2 AC5) conflicts with registry-as-source-of-truth + "limit change => new stores use new limit": which wins on load?
- Equipment: item representation (material id + qty 1?), `Material` lacks an item-type/category field needed for slot restriction; equipment slot definitions "part of prototype" (Assumption) but must be serialized in FR-026 -> which component holds them? Equipped perishables, equipped stat modifiers out of scope. `inventory.item.equipped/unequipped` only in Assumptions, not FR-021a. Equipment counted in weight? (yes via query).
- Merge ambiguity: with multiple partial stacks of a perishable which stack gets merged first (slot order); overflow into new stack uses fresh remaining; slot allocation order "seeded PRNG tie-break if needed" - should be purely deterministic by slot index (no PRNG draw).
- Decay formula: remaining -= decayRate * multipliers; combining container rate (stack stores `decayRate`) with difficulty multiplier and rounding order; when is rate updated (move pantry->pack)? expiry exactly when remaining <= 0 at which phase of tick (system order).
- Event payload shapes, order of multiple events in tick, and delivery buffering (event bus spec 010) unspecified. `retrieve` return value shape ("retrieved items") unspecified. Invalid quantity (0, negative, non-integer) behavior unspecified. transfer(self,self). Slot list representation (sparse with nulls vs dense occupied only; "slot count" semantic).
- Permission default of equip on self etc. `UnknownMaterialError` for transfer between inventories; dual-lock ordering irrelevant (single thread).

## 6. Acceptance scenarios / tests
- Store/retrieve: 3 slots, limit 10: store 8 -> 1 slot; +5 -> 10 and 3 overflow into new slot; full => InventoryFullError unchanged; retrieve 3 of 5; retrieve 5 of 2 => InsufficientItemsError.
- Stacks: Cheese(20)/Wood(50) 15+30 => 2 slots; 20/20 + 5 => second stack; removal frees slot; sum across stacks; JSON roundtrip.
- Queries: canStore/canRetrieve results (fix US3 AC1 math), availableSlots 0 when full, guarded ops never throw.
- Money: credit 100; debit 50; debit 30-50 => InsufficientFundsError; two-entity debit/credit conserve total; exact JSON balance.
- Transfer: 10 of 20 wood; DestinationFullError; InsufficientItemsError; money conserved; atomic (no partial).
- storeUpTo: {5,15}; {0,10}; {N,0}; stored+remainder==qty.
- Weight: limit 50, Stone 5 => 10 accepted then WeightLimitExceededError even with free slots; unlimited chest; availableWeight; roundtrip.
- Perishables: Cheese 576 ticks expires at 48h with `inventory.item.expired`; per-stack independent expiry; Wood never expires; remaining time exact in JSON; merge weighted average floor; decay multipliers.
- Equipment: equip/swap/incompatible/unequip with full inventory; roundtrip; combined totals.
- Permissions: locked chest AccessDeniedError; authorized trade passes; default open; rules roundtrip.
- Events: stored/retrieved/transferred emitted at tick boundary only; sync queries see new state same tick (SC-012); failed ops zero side effects (SC-003); deterministic slot layout; perf SC-001.

## 7. Size: L (many small features; perishables + permissions + equipment add breadth).
