## 0. Conventions

| Topic | Rule |
|---|---|
| IDs | `EntityId`, `MapId`, `TaskId`, `PostingId`, `OrderId`, `OfferId`, `JobId`, `MomentId`, `ReservationId` = non-negative safe integer. Monotonic counters, never reused, persisted in root `counters` (D-05). Content IDs (materials, recipes, terrain ...) = lowercase snake_case `string` (open vocab, 023 FR-005). |
| JSON | `JsonValue = null \| boolean \| number(safe integer) \| string \| JsonValue[] \| {[k:string]: JsonValue}`. Event payloads, task data, command payloads are `JsonValue`-compatible. No `unknown`/`any` in game code except the Zod/JSON boundary (AD11). |
| Maps keyed by ids | Never serialize an object keyed by integer-like keys. Use arrays of records sorted ascending by id (`standing: [{factionId,value,tradeAgreement}]`). Object keys that are strings (material ids) are allowed but serialization MUST sort keys (stable stringify). |
| Enums | Closed sets are TS `enum` (023). Serialized as the enum's string value except `SpeedSetting` (numeric). Zod via `z.nativeEnum`. |
| Errors | Domain failures return `{ok:false, error:{code:ErrorCode,message}}` at the command layer; library functions throw typed `Error` subclasses (spec names: `InventoryFullError` ...). `ErrorCode` is a string enum, member names = spec error names (`ContentLockedError` -> `ContentLocked`). |
| Time | `tick` = `time.tickCount` (int). `ticksPerHour=12`, `ticksPerDay=288`, `daysPerWeek=7`, `daysPerMonth=28`, `monthsPerYear=12` (year = 336 days). `toDay(tick)=floor(tick/288)` 0-indexed (UI shows +1). `tickOfDay=tick mod 288`. Always use the constant, never literal 288. |
| Randomness | Only through `Prng` named streams (D-03). Stream registry (names are API): `world.gen`, `site.gen`, `identity.names`, `housing.immigration`, `diplomacy.ai`, `diplomacy.resolve`, `skill.output`, `content.traits`, `ai.risk`, `ai.decide`, `ai.wander`. Pure derivations (A*, claim ordering, dominantSkill, finest scan) use deterministic tie-breaks (lowest id / lexicographic), never a stream. |
| Iteration order | Entities: ascending EntityId (== insertion order, IDs monotonic). Posting/order/zone/offer lists: ascending id. Content registries: file order then id. |
| Fixed point | See D-04 table. Nothing but `number` safe integers in state. Division = `Math.trunc`/`floorDiv`/`ceilDiv` helpers (`src/game/engine/FixedPoint.ts`, task 1.x); never `/` on state values. |

## 1. Decisions

### D-01 Behaviour runtime without JS async (conflict 1; AD3)
- **Amends 003 FR-009/012/015, US async stories; 010 FR-012; 002/004/005/012/013/014 wherever `await` appears.**
- No `async`/`Promise`/`await` in `src/game`. `walkTo`, `craft`, `purchase` etc. are **task handlers**: serializable step machines.
- `TaskRecord = { id:TaskId, type:string, priority:int, status:TaskStatus, phase:string, data:JsonValue, parentId:TaskId|null, waitFor:WaitCondition|null, createdTick:int, token:CancelToken|null }`.
  - `TaskStatus = Pending | Running | Waiting | Completed | Cancelled | Failed`.
  - `WaitCondition = {kind:Event, pattern:string, matchKey:string|null, matchValue:JsonValue} | {kind:ChildTask, taskId} | {kind:UntilTick, tick:int}`. `matchKey/matchValue` = optional top-level payload field equality (replaces `waitFor(predicate)`). The task system subscribes to patterns of `Waiting` tasks after load (subscriptions are never serialized).
  - `CancelToken = {category:Graceful|Ungraceful, reason:string}` (reasons: `entity_deleted`, `interrupted_by_priority`, `player_cancel`, `component_removed`, `unreachable`).
- `TaskHandler = { type; start(ctx,data):StepResult; step(ctx,record):StepResult; cancel(ctx,record,token):void }`; `StepResult = Continue | Wait(WaitCondition) | Done | Fail(reason)`. Handlers registered by `type` in a per-engine `TaskHandlerRegistry` (no giant switch). A handler may `ctx.spawnChild(type,data)` and `Wait(ChildTask)`; sequential "await chains" = one parent task with `phase` advancing as children finish.
- `TaskQueue` component: `{ tasks: TaskRecord[] (pending+current, ascending id), history: {taskId,type,outcome,tick}[] (capped `taskHistoryCapacity`=8) }`. One task `Running` per entity. Each tick the entity's highest-priority runnable task (priority desc, id asc) runs **one `step`**. A strictly higher-priority arrival cancels the running task with `Graceful interrupted_by_priority` at the next step boundary (handler rolls back, e.g. 014 FR-013a); changing the priority of a running task never interrupts it. `interrupt(entity)` = cancel running + clear pending. Entity deletion: `Ungraceful entity_deleted` to all; waiting parents fail.
- Required component removed mid-task: task `Fail('component_removed')`, never throws in the loop. Prototype serialization (003 US1 AC4) removed (D-05).
- Event: `task.finished` (4).

### D-02 Event bus (conflict 2; spec 010) — implemented by task 0.4
- `emit(topic,payload)` queues `{name,payload,depth}`; `processQueue()` drains FIFO at pipeline slot 20 and at `flush()`. **Amends 010 FR-011:** delivery set is resolved **when the event is processed**: every subscriber registered at that moment and matching receives it (including subscribers registered after emit, or after `load`). Matching subscribers are called in **global registration order** (exact and wildcard interleaved by subscription handle). A subscriber unsubscribed before its turn is skipped. `once` subscriptions are removed before invocation.
- `tick.begin {tick}` is emitted and **flushed immediately** at slot 0, so the queue is empty when systems start. 010 SC-001 holds at both ends of the tick.
- Depth: an event emitted outside any handler has depth 0; emitted while processing an event of depth `d` has depth `d+1`. `maxEventDepth = 16`; emit with depth > 16 is **not queued** and reported to the error sink with `kind: EventBusErrorKind.DepthExceeded`.
- **`waitFor`/Promise removed** (D-01).
- `subscribe(pattern, handler, options?:{once?:boolean}) : SubscriptionHandle` (positive int); `unsubscribe(handle)`. 010 FR-008's `(name, callback)` form removed.
- Subscriber exceptions are caught and passed to the injected `EventBusErrorSink(report: {kind: EventBusErrorKind, topic, message})`; processing continues. No `error.system-failed` event. The bus's own default sink ignores reports; `GameEngine` (1.8) injects a sink that collects to an inspectable array (`engine.errors`).
- Names: dot-separated lowercase kebab segments `[a-z0-9]+(-[a-z0-9]+)*`; wildcards `*` (exactly one segment) and `**` (one or more) only as the **last** segment; `inventory.**` does not match `inventory`. Invalid names/patterns throw `EventBusError` at emit and subscribe. A bare `*` or `**` pattern is allowed (global listener).
- Serialized: `EventBusState = { queue: {name:string, payload:JsonValue, depth:int}[] }` at root key `eventQueue`. Subscriptions never serialized. Payloads are deep-copied on emit by `cloneEventPayload`, which throws `EventBusError` for non-JSON values and for numbers that are not safe integers (Constitution II). API (all in `src/game/engine/EventBus.ts`): `EventBus` {`emit`, `subscribe`, `unsubscribe`, `processQueue`, `getQueue`, `serialize`, `restore`}, `isValidEventName`, `isValidEventPattern`, `eventNameMatches`, `isEventOf`, types `JsonValue`, `GameEvent`, `EventHandler`. There is no separate `flush()`: call `processQueue()`. Re-entrant `processQueue()` is a no-op.
- Emits outside a tick (bootstrap, command handlers between ticks) are queued and delivered at the next `processQueue()`/`flush()`.

### D-03 PRNG (conflict 2; spec 011; AD6) — implemented by task 0.3
- Algorithm PCG32 XSH-RR (O'Neill reference; multiplier `6364136223846793005`, default increment `1442695040888963407` is **not** used — each stream has its own odd `inc`). 64-bit values held as `[hi:uint32, lo:uint32]` pairs; arithmetic with 32-bit halves (no BigInt in the hot path).
- `Prng` (root): holds `seed` (0..2^32-1) and a name->stream registry. `stream(name): PrngStream` get-or-create **and persisted**; replaces `derive()`. Stream initial state = PCG seeding from four uint32 words derived from `(seed, fnv1a32(name))` (see golden note below); independent of how many values other streams or the root drew; two streams with different names differ.
- `PrngStream` integer API only: `nextU32()`, `nextInt(min,max)` (inclusive, unbiased rejection sampling), `chancePermille(p)` (0..1000, true with probability p/1000), `choice(array)`, `weighted(options, weights)` (positive integer weights, sum <= 2^32; draws in `[0,sum)`; fractional weights are NOT supported — callers convert to permille), `shuffle(array)` (in place, Fisher–Yates descending). `random()` float removed. Also `nextBelow(range)` (unbiased `0..range-1`). Validation errors: `PrngError` with clear messages (empty array, min>max, non-integer, negative/zero-sum weights, length mismatch).
- `Prng.create({seed?, entropy?})`: if no seed supplied, `entropy()` (must return a uint32) is called **exactly once**; the result is recorded in `initOptions.seed`. `GameEngine` receives `entropy` by injection (default in CLI/React host = host-side randomness; tests inject a constant).
- `setSeed(seed)` (tests/debug only): re-seeds; every existing stream is re-initialised from the new seed (same name -> same new sequence).
- `PrngState = { seed:int, streams: Record<name, {state:[int,int], inc:[int,int]}> }` (keys sorted by name) at root key `prng`. `serialize()/Prng.fromState()` exact round trip (a stream resumes mid-sequence).
- Pathfinding does not use the PRNG (D-21). 011 FR-016 fractional weights and `randomBool(float)` removed. 011 SC-005 (<1 KB) is relaxed to "<= 100 bytes per stream".
- Golden vectors committed in `Prng.test.ts`: the official PCG32 demo (initstate 42, initseq 54) and seed 12345/stream `main` plus a 1e6-draw checksum. Stream init uses a murmur3-fmix32/FNV-1a-32 word chain (not FNV-64); `PrngStream.fromInit(initState, initSeq)` is the reference seeding.

### D-05 Save format, ID counters, root keys, versioning, geometry (conflicts 3, 10; AD9)
- Root keys (authoritative, **amends 006 FR-004/004a, US1 AC1**): `version, timestamp, time, prng, eventQueue, initOptions, counters, systems, statuses, productionLedger, stewardship, entities, maps`.
  - `counters = { nextEntityId, nextTaskId, nextMapId, nextPostingId, nextClaimId, nextOrderId(production), nextOfferId, nextReservationId, nextJobId, nextMomentId, nextZoneEventId }` all ints. (`stewardship.nextOrderId` is separate.)
  - `systems = { [systemId:string]: JsonValue }`: global per-system state without an owning entity (reservations, zone merge offers, trader visits, pending wage payments, difficulty cache ...). Keys sorted. Each system owns one key and one Zod schema.
  - Component-borne (not root): SettlementProgress, SettlementChronicle, Identity, Dwelling, Citizen.home*.
- `timestamp`: injected by host via `save({timestamp})`; engine default `"1970-01-01T00:00:00.000Z"`; excluded from equality (006 FR-006a). No `Date` in `src/game`.
- Version: `CURRENT_SAVE_VERSION = 1`. A v0 fixture exists in tests only (migration chain `0->1` renames difficulty normal/hard -> steady/harsh and adds `counters`). Errors: `InvalidSaveFormatError`, `UnsupportedSaveVersionError` (newer).
- `load` unknown fields: root and component records are Zod `.strict()` -> reject; `initOptions` unknown fields are ignored (007). Unknown content ids (terrain/material/prototype) -> `InvalidSaveFormatError` naming file/path.
- Prototypes and registries are never serialized (003 vs 006); content pack is supplied to `new GameEngine(content)`.
- Maps: `{ id, gridType, width?, height?, params:{generator:string, seed:int, cellCount?:int, relaxPasses?:int}, cells:[{terrain}] }`. **Voronoi geometry (sites, Delaunay, polygons, adjacency, centroids) is a pure integer function of `(params)` regenerated on load** (sites in `[0,65535]^2`, exact predicates with BigInt in the builder, integer Lloyd). Terrain edits live in `cells`. Cell order and `neighbors(cell)` order (ascending cellIndex) identical on both grid kinds. Delaunay lib: implemented in-house (no float).
- `save()` is read-only: no task cancellation (006 assumption removed); in-flight tasks serialize as records (D-01). Save requested mid-tick is queued to the end of the tick (`SaveGame` is an Immediate command only legal between ticks).
- Byte-for-byte: `save()` = stable stringify (sorted object keys, arrays preserved), no `-0`, no non-integers (validated).
- Position component `{mapId, cellIndex}` is the sole location source; occupant index is derived and rebuilt on load.

### D-06 Engine bootstrap (conflict 3; spec 007)
- `new GameEngine(content: ContentRegistries, deps?:{entropy, errorSink})`; **instance** methods `newGame(options?)`, `loadGame(save)`. Both validate/parse fully into a temporary state, then swap; failure leaves the current state untouched (replaces `OutOfMemoryError`, which is dropped). Static `GameEngine.newGame` removed. Registries are per-engine (AD8).
- Method names (amend 007 FR-016): `getTime()`, `getState()` (readonly snapshot view, not live), `getEntity(id)`, `getEntities()`, `getMap(id)`, `getComponents(id)`; `save()`/`loadGame()`; `tick()`. `getGameTime` removed.
- "Starting entity counts" option removed. **FR-017 removed**: bootstrap requires the government faction prototype; missing -> `ContentValidationError`.
- `newGame` with no map options yields exactly one entity (government faction). With `mapSize` it additionally runs the world generator (2.1) which places: main map, a starting settlement kit (job board, throne room furniture, N starting settlers incl. one Town Crier). `MapSize { Small=0..}` mapping: Small -> 600-cell Voronoi (004 default), Medium 1200, Large 2400; difficulty never affects generation (027 FR-016).
- `game.started`/`game.loaded` are queued at bootstrap, delivered at the first `processQueue()`.
- Option typos: unknown fields ignored (007), but the CLI/Zod layer logs a warning list in the command result.

### D-07 Inventory (conflict 4; spec 005)
- Permission model: every mutating function takes `ctx:{actor:EntityId|null}`; `null` = system actor (bypasses rules). Rule evaluation: first matching rule wins; **no match -> allow**; no rules -> allow. `transfer` checks `Retrieve` on source and `Store` on destination for the actor; `InventoryOperation.Transfer` is retained as an alias for "both".
- Material (single schema owner = 022 loader, `MaterialSchema`): `{id,name,categories,stackLimit,weightMilli,valueMilli?,perishabilityTicks?}`. Stack limit source of truth = registry; **slots do not serialize `stackLimit`** (amends 005 FR-026, US2 AC5).
- Slot layout: `slots: InventorySlot[]` dense occupied slots in creation order; `slotCount` is capacity. Store fills existing partial stacks in slot order, then new slots. Merge of perishable stacks uses the first partial stack with `remaining` weighted floor (005 FR-020a). Deterministic, no PRNG.
- Equipment: `equipment: {name:string, restrictionCategory:string, materialId:string|null}[]` inside the Inventory component (serialized). Slot restriction matches a material `categories` entry.
- `store/retrieve` quantity must be a positive integer else `InvalidQuantityError`. `retrieve` returns `{materialId, quantity}[]` removed. Self-transfer is a no-op error `InvalidTransferError`.
- Weight in milli (D-04). **Errata:** 005 US3 AC1 example: with wood 8/50, limit 50, 2 free slots, `canStore(wood,60)` -> `fits:true, maxFittable:142`; tests use the corrected numbers.
- Money: a normal material; `credit` uses `storeUpTo` semantic + `InventoryFullError` when it cannot fit all.
- Events are emitted at call time into the bus queue (delivered at the drain); queries see state immediately.
- Decay: `remaining -= combine(combine(1000, zoneModifierMilli), difficultyDecayMilli)` per tick scaled by stack `decayRateMilli`; expiry when `remaining<=0`, evaluated in slot 3.

### D-08 Shared job-posting model (conflict 5; specs 016/017/019/020/021/027)
`JobPosting` (amends 017 FR-003):
```
{ id:PostingId, boardId:EntityId, jobTypeId:string, params:JsonValue, concurrency:int, slotsFree:int,
  recurrence:Recurrence, priority:int(0..100, default 50), urgent:boolean, wage:int(coins, default job-type wage),
  posterFactionId:EntityId, eligibility:Eligibility[], status:PostingStatus, blocked:BlockedReason|null,
  standingOrderId:int|null, deliverToZoneId:EntityId|null, ownerSystem:PostingOwner }
Eligibility = AdultHumanoid | FactionMember{factionId} | NotHostileToPoster | MinSkill{skillId,level} | TierUnlocked{tier}
PostingOwner = Zone{zoneId} | ProductionOrder{orderId} | Construction{jobId} | StandingOrder{orderId} | Player | Housing
```
- Eligibility is evaluated at **claim time** by the claimer. `NotHostileToPoster` (021 labour gate): ineligible if the integer mean of `standing[f -> posterFactionId]` over the worker's factions (excluding the poster itself) is `< -30`; a worker belonging to the poster is eligible. Construction postings carry `[AdultHumanoid]` (016 FR-001b).
- **Claim order** (amends 017 FR-007; resolves 017/020): key tuple `(priority desc, urgent desc, familiarityBucket desc, pathCost asc, postingId asc)`. `familiarityBucket = floor(level/10)` (0..10) of the job type's `skillDomain` skill (0 when no domain). 020's `skillAffinityBonus` is therefore ordering-only (bucketed), no additive score. **PRNG tie-break removed** (017 FR-007, US7; 018 US5 likewise -> lowest id). Equal-distance boards: highest priority/familiar, then lowest entity id. Greedy re-route: **off** (decided, not optional).
- `urgent`: set by systems for need-driven postings (haul food to starving household) or by player `SetConstructionPriority(urgent)`; no other source.
- **Which board gets what:** postings created by *systems* (construction, production orders, zone auto-posts, housing) are placed **immediately** on the nearest non-paused board on the target's map (path distance; tie lowest id) — they bypass Town Criers. Town Criers carry only *player-edited* postings on user-managed boards (`PostJob/RemovePosting/ModifyPosting`) and Steward runs (026). A board's `mode` (`SystemManaged|UserManaged`) governs who may edit it (017 FR-009/010), not whether systems may post.
- **Wage/payer:** `jobboard.job.completed` carries `{workerId, wage, outputs}`. Treasury system (019) listens, enqueues `PendingWagePayment{paymentId = claimId}` and pays from the Throne Room treasury of the *poster faction*; only the player government has a treasury. Wage `0` = no transfer. Job types may declare a default `wage` (content).
- **Completion emitters:** the system that executes a job emits `skill.work.completed {entityId, skillId}` once per completed claim (production -> crafter with recipe skill; construction -> builder `construction`; gathering/haul -> worker with job-type `skillDomain`; trade -> both parties, skill `trading`). The board only emits `jobboard.job.completed`.
- `skillDomain` and wage live on the JobType (022). `urgency`/familiarity "experience tags" dropped.
- 016 status mapping: ConstructionJob `suspended` == posting `suspended` with `blocked`; `paused` == board-independent `paused` flag on the job (posting withdrawn from claims). 016 `construction.job.started` = construction phase begins (progress starts); `construction.job.claimed` added for claim.
- Town Crier = Citizen with a `TownCrier` component (`{status, boardQueue, carrying:PendingUpdateRef[]}`); fleet = count of such citizens; created by commands `AppointTownCrier/DismissTownCrier` and one is designated by the starting settlement kit. Steward cannot be a crier; criers cannot be Steward. Crier destroyed -> its carried changes are lost (017 edge), queued ones survive (they live in `systems.jobboard.pendingUpdates`).
- Pending updates: `PendingBoardUpdate {updateId, boardId, changes: BoardChange[], origin:Player|Steward, ownedRunRef?}`; withdrawal of a still-pending add removes both (no-op on delivery).
- Pause sources: `PauseSource {Player, System}` tracked separately on board; board is paused if either; zone re-activation clears only System.

### D-09 Reservations, locks, tool use (conflict 5; 014/016/018/019)
- `ReservationService` (state in `systems.reservations`): `Reservation {id, kind:Lock|Haul|Tool|Payment, holderId:EntityId, inventoryOwnerId:EntityId, materialId, quantity, createdTick}`. Reserved quantity is excluded from `StorageQuery.availableTo(requester)` for everyone except the holder.
- Material lock for crafting (014 FR-013) = `kind:Lock`; released on completion/interrupt.
- Excluded from material queries (018 FR-011): inventories of `BuildSite`, `loose_pile` is included (it is a source), carried hauler stock is NOT claimable, household storage on dwelling tiles (029), Inventory with `queryable:false`. Inventory component gains `queryable:boolean` (default true).
- "Locked chest" in 018 = inventory permission denies the requester (`AccessDenied`); no lock mechanic.
- Tools: a builder/worker reserves a tool item (`kind:Tool`) before fetching; a held tool is simply in the worker's inventory and never deposited. One tool, many jobs: second claimer's job suspends with `MissingTool` and re-evaluates each tick.
- Stockpile "sources": hauler-carried items are not sources (018 blocker 1 resolved).

### D-10 Production (conflict 6; spec 014)
- **Two commands** (014 US8.3 vs FR-013a): `CancelProductionOrder` stops the order, in-flight craft finishes; `CancelCraft{workstationId}` interrupts (return locked inputs, progress 0).
- Material registry owner: 022 `MaterialSchema` (D-07). 014 FR-001 references it.
- Recipe variants (014 US9.2): **not supported**; variant recipes are separate recipe entries. Multi-step chains (014 FR-010 auto-prerequisite crafting) **removed**: a craft whose input is missing reports `MissingInput` (with `noProducer`/`causeRef` per 025) and gathers from stock; intermediates are produced via their own production/standing orders. 014 US3 becomes "chain via orders".
- Skill duration: D-20 formula. Restrictions: `workstation` tag, `room` zone type id, `skill{id,min}`, optional `workstationQuality` removed. Room restriction = the workstation lies on a tile of an **active** zone of that type; failing -> `MissingRoom{zoneTypeId}` (025 maps 015 gaps via `ZoneRequirementsUnmet` on the zone subject).
- Crafter death: locked inputs return to the workstation inventory (work inventory) or, if crafting by hand, drop as `loose_pile` at the crafter's cell. Workstation destroyed: contents dropped as loose pile.
- 0-duration recipes complete in the step they start (progress 0->done, same tick); one active crafter per workstation.
- Orders: `ProductionOrder {orderId, workstationId, recipeId, remaining, priority, status:Active|Paused|Completed|Cancelled}` stored in component `ProductionOrders` on the workstation entity; each active order posts a `craft.produce` posting (ownerSystem ProductionOrder). Standing orders (026) post their own runs.
- Events per 4. `production.crafting.failed` reserved for hard failures (e.g. recipe removed): emitted with `reason`.

### D-11 Zones & rooms (conflict 6; spec 015, 009)
- **Rename:** spec 009 "Room" -> `Site` (`SiteGenerator`, `GeneratedSite`, `SiteSize`, `SiteScenario`). 015's Room stays. Generator is not stateless: it takes `Prng` stream `site.gen`; explicit `options.seed` -> private `Prng(seed)`; absent -> `seed = site.gen.nextU32()` recorded in the returned `GeneratedSite.params`. `generate` returns data to insert; it does not mutate game state. `objectCount` is not a param (only `objectDensity` permille 0..1000, 500 = default 5-10). Retries: 8.
- Timing: requirement/room evaluation is **dirty-flag driven in slot 9 of the same tick** as the triggering change; status and `zone.requirements.*` events appear that tick; *effects* (modifiers, activity-unlock queries) take effect from the **next tick**. On load: silent rebuild (no events); `zone.requirements.*` only on later transitions.
- Designation: tiles must be on one map. `DesignateZone` with disconnected tiles creates one zone per connected component (ids ascending by min cellIndex). Tile already in another zone -> command rejected `TileAlreadyZoned{cellIndex,zoneId}`; `reassign:true` option moves tiles. Remove-tiles disconnecting a zone splits it: largest part (tie: lowest min cellIndex) keeps the id, others get new ids ascending.
- Merge: when a separating wall disappears between same-type zones, system creates `MergeOffer{offerId,zoneAId,zoneBId}` in `systems.zones.mergeOffers` + `zone.merge.offered`; `ConfirmZoneMerge{offerId,accept}`; survivor = lower id. Offers lapse if zones change.
- Enclosure: perimeter neighbours (non-zone side) must contain a wall/door entity; map border counts as **not enclosed**; neighbour zone tiles that are not walls do not enclose; doors open or closed enclose and are **passable for pathing when closed** (D-21).

### D-12 Trade protocol (conflict 7; spec 019)
- Geography: buyer pathfinds to seller (task `trade.approach`) to path cost <= 1 cell, then emits the offer. Seller `sellsItems` entities do not move while an offer is pending.
- State machine per `TradeOffer{offerId, negotiationId, round, buyerId, sellerId, requested:Item[], offered:Item[], currencyCoins:int, createdTick, expiryTick}`: processed by TradeSystem (slot 10), ascending offerId:
  1. refuse `self-trade` silently; `faction-hostile` if standing gate; `unknown-item-value` if any item lacks `valueMilli`; `insufficient-stock` if seller lacks full quantity (**no partial counters**, amends 019).
  2. `minAcceptableMilli = ceilDiv(sum(valueMilli*qty) * priceMultiplier‰ * (1000 + marginRate‰), 1_000_000)`, `priceMultiplier‰ = base * agreementDiscount` (agreement => `*900/1000`), `marginRate‰ = minimumMarginRate + traitMarginAdd` (Greedy +50). Offered value = `currencyCoins*1000 + sum(valueMilli*qty of barter items)` **at plain `valueMilli` (no multiplier/margin on received goods)**. Accept iff `offeredMilli >= minAcceptableMilli`.
  3. Accept -> **execute in the same step** (atomic: pre-check both inventories with `canRetrieve/canStore`; both transfers or none). No "accepted, awaiting execution" state. Failure -> `trade.execution.failed {reason: buyer-inventory-full|seller-inventory-full|seller-deleted|buyer-deleted}`.
  4. Below threshold -> `countered` with `counterCoins = ceilDiv(minAcceptableMilli - barterMilli, 1000)` (>=0). The buyer's next trade step re-proposes with `round+1` if it can afford and still wants; round > `maxNegotiationRounds`(3) -> `expired`.
  - Offers expire after `offerTimeoutTicks`=24 if unresolved (seller gone). Pending offers serialize in `systems.trade.offers`.
- Hostile gate flips mid-negotiation (standing crosses `-30`): TradeSystem cancels affected offers with `trade.offer.cancelled {reason:'faction-hostile'}` (subscribes to `diplomacy.standing.changed`).
- Reserved goods: no reservation needed (offers resolve atomically in a step); simultaneous buyers resolved by ascending offerId.
- Treasury = sum of currency in storage furniture on active Throne Room tiles (via StorageQuery); wage payments: `PendingWagePayment` in `systems.treasury.payments`, retried each tick in order of `paymentId`; no containers -> `treasury.unavailable` once per day.
- Barter value, 019 US4 "applies multiplier on Stone lookup" clarified by item 2 above. Trade skill/Greedy trait: margin add only (D-20).

## 8. Implementation decisions (made while building; no owner review needed)

### D-31 Time, pipeline and counters (tasks 1.1; `src/game/time`, `src/game/engine`)
- `GameTime` (`time/GameTime.ts`) is a clock object, not commands: `pause/resume/setSpeed/setTickIntervalMs` methods (applied by the session, D-23), `advance()` (+1 tick, called only by the pipeline at slot 2), `restore(json)` (strict Zod, throws `GameTimeError`, no fallbacks), `serialize()`. It emits `game.paused/resumed/speed.changed` only when the value actually changes. `tickIntervalMs` is an integer `1..3_600_000`. Calendar helpers are pure functions of the tick (`toDay/toWeek/toMonth/toYear/tickOfDay/hourOfDay/toGameHours`; hours are whole hours).
- `TickPipeline` (`engine/TickPipeline.ts`): `enum TickSlot` (0..20) pinned to section 2 by a test that parses this file. Systems register `{id, slot, order, run(ctx)}`; execution order is `(slot, order, registration sequence)`. `ctx.tick` = `tickCount + 1` for the whole tick (so slots 0-1 see the tick being processed), `ctx.tickOfDay = tick mod ticksPerDay`. Built-ins: `tick.begin {tick}` emitted and flushed before any slot-0 system, `time.advance()` at the start of slot 2 (slot-2 systems see the new count), `bus.processQueue()` after the slot-20 systems. Paused => `tick()` returns false and does nothing. Registering during a tick takes effect next tick. A throwing system propagates.
- `AutoRunner` (`engine/AutoRunner.ts`): one chained timer through an injected `Scheduler {schedule, cancel}` (default `createTimerScheduler()` over `setTimeout`); re-reads `time.realDelayMs()` before every tick; no catch-up; keeps polling while paused (ticks are no-ops); if `tick()` throws the runner stops and rethrows.
- `IdCounters` (`engine/IdCounters.ts`): `enum CounterName` values = the D-05 root `counters` keys (`ProductionOrderId` = `nextOrderId`); **ids start at 1**; `allocate/peek/serialize/restore`; restore requires every key and rejects unknown keys. `EntityStore.restore` requires saved ids `< nextEntityId`, so restore counters first.
- Integer division inside `GameTime` uses a private exact `divideFloor`; the shared `FixedPoint.ts` of section 0 is not part of this task.

### D-32 ECS conventions (task 1.2; `src/game/ecs`)
- Component names are PascalCase (`/^[A-Z][A-Za-z0-9]*$/`), prototype ids lowercase snake_case. The 023 naming rule is relaxed to allow PascalCase **object-literal property names** (`{ Position: {...} }`) in `eslint.config.js`, because component names are map keys.
- `ComponentDefinition<Name, Data> = {name, schema: z.ZodType<Data>, defaults()}` made by `defineComponent`; definitions are plain values registered in a per-engine `ComponentRegistry`. `hasComponent(entity, def)` narrows to `WithComponent<typeof def>`.
- Entity JSON is `{id, prototype, components}`; `EntityStore` state is `{entities: Entity[]}` ascending by id (root key `entities`). Prototypes = `{id, components: {Name: partialOverrides}}`; merge order defaults < prototype < spawn overrides; spawn overrides may only name components the prototype has.
- Deletion is two-phase (`requestDelete`, `flushDeletions` at slot 17); pending entities are hidden from `entities()` and queries unless `includePendingDelete`; `serialize()` throws while any are pending. `entity.deleted.name` comes from `addBeforeDeleteHook` hooks (first non-null). `entity.spawned` reads `mapId/cellIndex` from a `Position` component when present, else null.
- Queries: path `Component.field[.sub]`; matcher = JSON value (deep equality), `{min?,max?}` (inclusive, numbers only) or `{contains}` (list fields); an object literal with only those keys is read as the operator. Missing component/field never matches. Everything is a full scan in ascending id order (no indexes, no caches).
- Relationships (E-02 detail): `RelationshipDefinition {name, component, field, direction: Forward|Inverse, many}`; the field holds an id, an id list or null. Forward reads the holder's field; Inverse scans for holders. `registerPair` registers both. `getRelatedEntities` throws `DanglingReference` for deleted forward targets; `getRelatedEntity` returns the lowest id or null; `traverseRelated` is breadth first, depth 1..5, visited set. `clearReferencesTo(store, registry, deletedId)` clears forward references and is meant to be called per removed entity at slot 17 by the engine.

### D-33 Task runtime and behavior-tree core (task 1.3; `src/game/task`, `src/game/behavior`)
- **Scheduling** (refines D-01): per entity (ascending id) at slot 6: finish pending cancellations -> wake `UntilTick`/`Predicate` waits -> run exactly one step of the `Running` task, else `start` the best `Pending` one (priority desc, id asc). A woken task is `Pending` with `wake != null` and resumes through `step`, not `start`. Cancellation is *requested* by setting `token` (arrival of a strictly higher priority, `cancel`, `interrupt`, parent finished) and carried out at the start of the entity's next slot-6 turn; the arrival starts in that same turn (SC-005). Entity deletion cancels synchronously and ungracefully from a `beforeDelete` hook. A task that never started is removed without calling `handler.cancel`. Raising a *pending* task above the running one counts as an arrival; changing the running task's priority never interrupts. A child never interrupts its own ancestor.
- **Record additions to D-01**: `TaskRecord.wake: {kind, data}|null` (why the task was woken; cleared after its next step) and `TaskHistoryEntry.reason: string|null`. `CancelReason.ParentFinished` (`parent_finished`) added: children still alive when their parent completes or fails are cancelled gracefully. `TaskQueue` validation: ids ascending, at most one `Running`, `waitFor` set exactly while `Waiting`.
- **Waits**: serialized `WaitCondition` kinds `event`, `child-task` (same entity only, usually from `ctx.spawnChild`), `until-tick`, and the added `predicate {predicateId, params}` evaluated once per tick for the waiting entity from a per-engine `WaitPredicateRegistry`. Event waits use one `**` bus subscription created in the `TaskSystem` constructor plus an in-memory index of entities with event waiters (`rebuildWaitIndex()` after `EntityStore.restore`); subscription order therefore never depends on a save. Wake data: event payload / `{taskId, outcome, reason}` / `{tick}` / null. A wait on a task that is no longer queued wakes immediately with its history outcome (or null). The minimum wait is one tick.
- A handler may declare `requires: string[]` of component names; if one is missing when the task is due, the task fails with `component_removed` without calling `cancel`. Exceptions thrown by handlers propagate out of the tick (as for pipeline systems).
- **Behavior trees**: DSL = D-15 (`run_tree` action with `params.treeId`, reserved id). Node ids and tree ids are lowercase snake_case; params values are string or integer. **Depth 5 is checked per tree** (root = depth 1, `run_tree` counts as a leaf), not through references; reference cycles are rejected at load and reference chains are capped at `maxSubTreeNesting = 8`. Trees load atomically via `BehaviorTreeRegistry.registerAll`. Conditions and actions are separate registries, both `(ctx) => success|failure|running`.
- **Interpreter** has memory: `AiState` (`{treeId, currentNode, running, lastActionTick}`, D-25 plus `running`) stores the child-index path to the running leaf (through `run_tree` via index 0). A running leaf is resumed directly; selectors/sequences do not re-evaluate earlier children while a descendant runs. A finished tree restarts at the root next tick. Saved paths are validated against the tree on use (`InvalidState`, no fallbacks). The slot-5 orchestration (utility choice, when to call `tick`) belongs to task 2.4; `utilityScoring.ts` only fixes the hook shape (`UtilityFactor`, `pickBestCandidate`: `base + sum`, ties lowest index).
- File layout note: `tsconfig.tools.json` now references `src/game` so `tests/` can import game code (integration test `tests/integration/taskBehaviorSaveLoad.test.ts`).

### D-34 Maps and terrain (task 1.4; `src/game/map`)
- **Map JSON** = D-05 plus `parentId: int|null` and `links: [{cell, targetMapId, targetCell}]` (ascending source cell, one link per cell). Square maps carry `width/height` and no `cellCount`/`relaxPasses`; Voronoi maps carry `params.cellCount` and no `width/height`; `relaxPasses` defaults to 2 and is saved explicitly. Seed is an integer `0..2^32-1`. Root key `maps` is an array ascending by id; `MapRegistry.restore` needs counters restored first and requires ids `< nextMapId`, parents with a smaller id, link targets that exist.
- **Voronoi build** (`voronoiGeometry.ts`): `Prng.create({seed}).stream("map.voronoi.sites")` draws distinct sites; Lloyd moves each site to the exact integer centroid (BigInt shoelace, halves up) of its Voronoi cell clipped to `0..65535`; final cell order = `floor(sqrt(cellCount))` horizontal bands by y, then x, then y; adjacency = Delaunay edges (Bowyer-Watson with a far super triangle; in-circle uses a double filter with a conservative error bound and falls back to BigInt, so the sign is always exact). Golden: 64x64 cells, seed 42, 2 passes, `hashGeometry` = `44ccef4c50a00a3e`.
- **Units**: square coordinates are milli-tiles (tile pitch 1000, centre at +500); Voronoi coordinates are the 0..65535 site units. `MapGeometry.stepUnit` is an upper bound of the centroid distance between adjacent cells (rounded up), to be used as `unit` of the D-21 A* heuristic.
- **Terrain registry**: `TerrainDefinition {id, moveCost: MoveCostClass, passable, blockReason}`; impassable terrain must have `water` or `impassable_cliff`, passable none. `blockReason(cell)` = impassable terrain reason, else the entity obstruction (`wall, locked, furniture`), else null. Obstructions are runtime-only, set by owner systems via `GameMap.setObstruction` (event `map.cell.obstruction.changed {traversable}` = effective traversability). A terrain change that flips passability emits only `map.terrain.changed` (D-21 invalidates on either event).
- `fill(terrain)` is silent (generation time, before `map.created` is consumed); `setTerrain` emits `map.terrain.changed` only when the value changes. `map.created` is emitted by `createMap`.
- **Occupants**: `OccupantIndex` (ascending ids, derived, rebuilt from `Position`); `Position` schema `{mapId>=1, cellIndex>=0}` strict. Placement or moves into a non-traversable cell throw `MapError(NotTraversable)`. The registry updates the index; the caller writes `Position`.
- **Links/travel**: links are map-level one-way records, `linkMaps({bidirectional})` creates both directions; `travel(entityId)` follows the link of the entity's cell atomically and emits `entity.map.changed {entityId, fromMapId, toMapId, cellIndex}`. Door/portal Transition entities (3.5) may call `transferEntity` instead. `deleteMap` is rejected while entities stand on the map, it has sub-maps, or another map links into it (D-21).
- **MapSize** (`mapDimensionsFor`): Voronoi 600/1200/2400 cells (D-06); square 30x20, 40x30, 60x40 (same counts).

### D-35 Inventory details (task 1.5; `src/game/inventory`)
- **API shape**: free functions, `ctx: InventoryContext = { materials, actor, bus?, resolver? }` first (D-07 `actor`), then the live `Entity`, then `materialId`, `quantity`. Queries take `materials` or only the entity. The reservation primitive (D-09) is task 3.2 and is not built here; the data shape needs nothing more than `queryable` and `getTotal`/`canRetrieve`.
- **Permission targets**: `{kind: entity|faction|role|anyone}`; `anyone` was added so "deny everybody except ..." is expressible. Faction and role membership come from an optional `ActorResolver` in the context (no resolver: faction/role rules never match). A `Transfer` rule matches `Store` and `Retrieve`; `Equip` covers `equip` and `unequip`. Order of checks: quantity, material, inventory present, permission, availability, capacity.
- **Errors**: `InventoryFullError` when slots are the shortage, `WeightLimitExceededError` when only weight is; transfers use `DestinationFullError` for the slot case. `InsufficientItemsError` takes precedence over destination errors in `transfer`.
- **Retrieve order**: soonest-to-expire stack first, then smallest, then lowest slot (reduces fragmentation; deterministic). `transfer` moves portions with their freshness and merges them at the destination with the FR-020a weighted floor.
- **Events**: `transfer` emits only `inventory.item.transferred` (no stored/retrieved pair); `credit`/`debit` emit `stored`/`retrieved` for the currency; `inventory.item.stack.merged {entityId, materialId, quantity}` is emitted only when a perishable store merges into an existing stack, quantity = items merged in. A swap emits `unequipped` then `equipped`.
- **Money**: `credit` is all-or-nothing (`InventoryFullError`/`WeightLimitExceededError`, balance unchanged); this resolves D-07's "storeUpTo semantic + InventoryFullError" without breaking SC-003. Balance counts general storage only. Currency id lives on `MaterialRegistry` (default `silver_penny`).
- **Weight and equipment**: equipped items count toward weight; equip/unequip are weight neutral and only check slot room. Equipped items drop their perishable timer and restart fresh on unequip. `getTotal`/`getAllItems` include equipment; `retrieve`/`canRetrieve` do not.
- **Component shape**: `{slotCount, weightLimitMilli|null, ownerId|null, queryable, slots, equipment, rules}`; slot `{materialId, quantity, remainingMilli|null, decayRateMilli|null}` (nulls instead of omitted fields, both set for perishables). Reduced `slotCount` below contents is legal (free slots clamp to 0). `ownerId` is informational.
- **Decay**: `decayInventory(entity, bus, {zoneModifierMilli, difficultyDecayMilli})` subtracts `combine(combine(combine(1000, zone), difficulty), stackRate)` milli-ticks per call (`combine` = 027 FR-014, in `inventoryMath.ts`); a stack at or below zero expires whole. The slot-3 system itself is registered by the engine bootstrap (1.8).


### D-36 Save format implementation (task 1.6; `src/game/save`)
- **API**: `saveGame(parts, {timestamp?}) -> string` (canonical `stableStringify`: sorted keys, integers only, no `-0`), `serializeGame` (root object), `parseSave(input, {sections, migrations?}) -> ParsedSave` (parse + newer-version reject + migrate + strict validation, touches no state), `loadGame(input, parts, {migrations?}) -> LoadResult`. `GameSnapshotParts = {time, prng: {prng}, bus, counters, store, maps, tasks, initOptions: {options}, sections}`; the engine (1.8) builds one per game. `prng` and `initOptions` are holders because load replaces the `Prng` object and the options value.
- **Restore order** (dependencies): counters, time, prng, event queue, entities, maps, `maps.rebuildOccupants(entities)`, `tasks.rebuildWaitIndex()`, init options, then registered sections ascending by `order` then registration. Subscriptions are never saved; systems create theirs at construction.
- **Atomic load**: `parseSave` validates everything cheap before any mutation (SC-004). If applying still throws, the previous state (captured with `saveGame` + `parseSave` first) is re-applied and the failure is rethrown as `InvalidSaveFormatError` (cause kept). Call `loadGame` between ticks with no entity pending deletion (`EntityStore.serialize` requires it).
- **Extension mechanism**: `SaveSectionRegistry.register({key, location: Root|Systems, schema, serialize, restore, order?, defaultForOlderSaves?})`. `Root` sections own a root key (`statuses`, `productionLedger`, `stewardship`); `Systems` sections own a `systems.<key>` entry. Root is strict: unregistered root keys or `systems` entries are rejected; registered sections are required in current-version saves. `defaultForOlderSaves` supplies the value only for saves that were migrated (a section introduced after that save's version), so a new section needs no empty-handed migration step. Schemas must be `z.ZodType<JsonValue>` (integers only).
- **Migrations**: `migrations/MigrationRegistry` holds one step per `fromVersion` (`n -> n+1`) over raw JSON; `createDefaultMigrations()` is the built-in chain, `currentSaveVersion` (saveTypes.ts) must be raised together with a new step (a test checks coverage). `migrateV0ToV1` renames `initOptions.difficulty` normal/hard to steady/harsh, adds `counters` derived from the highest entity, map and task ids (so no id is reused) and an empty `systems`.
- **Validation split**: root and core shapes are Zod here; `time`, `counters`, `entities`, `maps` are validated deeply by their own `restore` (strict, typed errors) and wrapped. `initOptions` is `{seed, difficulty: Difficulty, startingTier: string|null, mapSize: MapSize|null}` and ignores unknown fields (007). `Difficulty` enum lives in `save/initOptions.ts` until 027 moves it.
- **Hash helper**: `hashText`, `hashSaveText` (timestamp neutralised) and `hashGameState(parts)`: 64-bit two-lane FNV-style hash, 16 hex characters, for determinism tests (not for security).
- **Fixed point**: `engine/fixedPoint.ts` (lowercase file name, since the 023 file-name rule needs an export named after a PascalCase file): `FixedUnit {Int, Milli, Permille}`, `decimalToFixed` (exact via decimal text, rejects values needing rounding), `fixedPointSchema(unit)` for the content loader (1.7), and `floorDiv/ceilDiv/truncDiv`. This is the helper module D-0 called `FixedPoint.ts`.

### D-38 Engine host (task 1.8; `src/game/engine/GameEngine.ts`)
- **Atomicity**: `newGame` validates options (`InvalidOptionsError`), the system graph and the government prototype, and creates the `Prng` (the only entropy draw) before any mutation. The mutation phase resets the persistent subsystems in place (hosts keep their bus subscriptions) and, if an init hook throws, re-applies a save taken just before (`GameEngineError` kind `InitFailed`). `loadGame` uses the save module's rollback and the same recovery for failing hooks. A failed call therefore never changes the visible game. A `newGame` without seed and without an injected `entropy` is `GameEngineError` kind `MissingEntropy` (no `Math.random` in `src/game`).
- **Option messages**: one sentence per problem, joined by a space: `Invalid difficulty: 'x'. Valid values: peaceful, steady, harsh.`; `Invalid startingTier: ... Valid values: hamlet, village, market_town, chartered_town.`; `Invalid mapSize: 123. Valid values: 0 (small), 1 (medium), 2 (large).`; `Invalid seed: 1.5. Must be an integer from 0 to 4294967295.`; non-objects: `Invalid options: expected an object.` Unknown names are ignored and returned as `ignoredFields` (D-06 typo warning). Stored `initOptions.startingTier` is the tier string (default `hamlet`).
- **Bootstrap entities**: only the `government_faction` prototype is spawned. `SettlementProgress` (027) and `SettlementChronicle` (028) do not exist yet and are **not stubbed**: the owning tasks add the components to the prototype's JSON in `engine-prototypes.json` and register them with `registerSystem({components})`. `mapSize` creates the main Voronoi map (`world.starting-map` init hook, first passable terrain of the pack, seed = game seed) until the world generator (2.1) replaces that hook.
- **Events**: `game.started {seed, difficulty, startingTier}` is queued after the spawn (delivered at the first `processQueue`, D-06). `game.loaded {tick}` is emitted after a successful load **and the queue is drained once immediately**, so `loadGame(x)` followed by `saveGame()` equals `x` (007 US2); the previous queue is delivered in the same drain.
- **Facade**: `getState()` is a summary (`hasGame`, time view, init options, entity and map counts); the complete state is `saveGame()`. `getEntity/getEntities/getComponents/getMap` return deep copies (entities flagged for deletion are hidden). `getTime()` returns tick, pause, speed, interval, day, tickOfDay, hourOfDay.
- **System registration**: `engine.registerSystem(EngineSystemDefinition)` is the single extension point (id, slot/order/run, dependencies/init, components, saveSection, commandHandlers). New-game reset restores each registered save section to the state it had when it was registered. Command and query registrations are stored by kind and name (`getCommandHandler`, `getQuery`) and dispatched by the session facade (D-39).
- **Lazy content wiring**: prototypes and behavior trees of the pack are registered on the first `newGame`/`loadGame` so that later systems can register components and handlers after construction. Prototypes using unknown components raise `ContentValidationError`; trees naming unregistered handlers are left unloaded with a note in `engine.warnings` (retried at the next game start).

### D-39 GameSession facade (task 1.9; `src/game/api`)
- **One registration path**: `registerSystem({ commandHandlers: { kind: defineCommand({schema, handler, mode?, requiresGame?}) }, queries: { name: defineQuery({schema, run}) } })`. The engine stores `CommandRegistration` / `QueryRegistration` (duplicates are `GameEngineError`); the session looks them up at dispatch time, so systems registered after the session still work. The kernel commands (NewGame, LoadGame, SaveGame, Pause, Resume, SetSpeed, SetTickInterval, Step) and kernel queries are registered by the session itself through the same path (system `api.session`). Command `kind` values are kebab-case (`new-game`, `set-speed`); schemas validate the command object **without** `kind` and must be idempotent (handlers re-parse).
- **Result shape** (supersedes the `code`/`details` names of section 3): `{ok:true, commandId, queued, data, events, droppedEvents}` | `{ok:false, error:{kind:ApiErrorKind, message, issues?}}`. `ApiErrorKind` values: invalid-command, unknown-command, invalid-payload, no-game, invalid-options, missing-entropy, invalid-save-format, unsupported-save-version, init-failed, invalid-argument, not-found, unknown-query, command-failed, predicate-failed, replay-failed, internal. `InvalidSpeed`/`InvalidTickInterval` are reported as `invalid-payload` (the schema rejects them first). Command ids come from one counter per game (every accepted command, immediate ones too), saved in `systems.commandQueue` and reset by NewGame. `ok` is an allowed 2-letter identifier (eslint `id-length` exception).
- **Payload rule**: payloads are JSON with safe-integer numbers only (Constitution II); a float anywhere is `invalid-payload`.
- **Queue is game state**: pending commands live in save section `systems.commandQueue` `{nextCommandId, pending[]}` (included in the state hash, restored by load), so a save between dispatch and the next tick keeps them. Slot 1 (`order -1000`) applies them FIFO, emitting `command.applied` / `command.rejected {commandId, commandKind, code}`; a handler that throws is rejected without rollback of its own partial changes (handlers validate first).
- **Paused clock**: `Step` while paused runs no tick (slot 0 is a no-op) but flushes the queue once (D-23 "applied at the next step"), returning `ticksRun: 0`. Immediate commands drain the event bus afterwards so `game.paused` etc. are delivered even while no tick runs. NewGame also drains once so `game.started` is part of its result.
- **Log**: `commandLog` entries are `{commandId, tick, appliedTick, command}`; `tick` = tick count at dispatch (replay key), `appliedTick` = the slot-1 tick for queued commands (null while waiting). NewGame is logged with the seed actually used (`options` normalised), so replay needs no entropy source. `runUntil` is logged as one `step` with the ticks it ran. Rejected/invalid commands are not logged. `replay(log, {expectedHash?})` dispatches each entry when the session reaches its `tick` (NewGame/LoadGame exempt), stops at the first failure and returns the final hash.
- **Views** (`Views.ts`): readonly JSON built from copies; `query.run(name,args)` additionally copies and JSON-checks every result (`defineQuery` runs the same check), so nothing from the engine leaks. Kernel queries: `state, time, entities, entity, maps, map, cell, settlement (placeholder), event-log, pending-commands`; args are a JSON object (`{}` default). Typed `SessionQuery` methods return null for a missing map/cell/entity. The event buffer (`recentEventLimit`, default 256) is a session convenience, not saved or hashed; every result carries the events of its call (`droppedEvents` counts overflow).

### D-41 Pathfinding (task 2.2; `src/game/pathfinding`)
- **API** (refines D-21): `PathfindingService` via `registerPathfinding(engine)` (system id `pathfinding`, idempotent per engine; the engine does not auto-register it, the composition root or the first system that needs it calls it). `findPath(mapId, from, target, {maxExpansions?}) -> PathResult` (`found {cells, cost}` | `already-there` | `no-path {reason: unreachable | invalid-position | budget-exceeded}`), `findRoute(fromLoc, toLoc, options) -> RouteResult` (`steps: {mapId, cellIndex}[]`), `reachable(mapId, from, maxCost?)` (012 FR-010), `findPathBreak(mapId, from, cells)` (FR-006 validation: index of first bad step or null). Queries `find-path`, `find-route`, `reachable`. Results are plain JSON (`pathResultSchema`, `routeResultSchema`), safe to store in task data.
- **Pure search**: tie-break `(f, h, cell index)`; neighbours ascending; cost = sum of entered cells' move cost; start may be blocked, target must be traversable (else immediate `no-path/unreachable`); out-of-range or unknown map -> `no-path/invalid-position`; `maxExpansions` default 200000, exceeded -> `no-path/budget-exceeded`. Heuristic: square `floor(|dx|+|dy| / 1000) * minStepCost`; voronoi `floor(sqrt(dx^2+dy^2) * minStepCost / stepUnit)` computed with integers only; `minStepCost` = lowest move cost among passable terrains of the content.
- **Cross-map** (D-21 "flattened"): in this codebase transitions are the map-level links of D-34 (door/portal entities of task 3.5 will call `transferEntity`; if they later add links, routing already sees them). Edge cost = 10 + landing cell cost; heuristic 0 (Dijkstra order) because a link may beat any geometric bound; ties `(cost, mapId, cell)`. Link into a non-traversable landing cell is not an edge. Routes are not cached; a start map with no outgoing links answers through the cached `findPath`.
- **Cache**: bounded LRU (default 1024 entries) of same-map outcomes. An entry is valid only for the same `GameMap` object and unchanged `GameMap.revision` (new synchronous counter bumped by `setTerrain`/`fill`/`setObstruction`/`addLink`; not saved), so stale hits are impossible even within a tick before the bus drains; `map.terrain.changed` and `map.cell.obstruction.changed` additionally purge the map's entries (D-21). Entries store their expansion count so cached answers honour any `maxExpansions` exactly like a fresh search (cold == warm, also across budgets); budget failures and trivial results are not cached. The cache is derived state: **not serialized**, cleared in the system's init on every `newGame`/`loadGame`.
- **Events**: pathfinding emits none and the catalogue gets no `path.*` topics; movers poll `findPathBreak` or react to the existing map-change events (013 re-plans).
- **Performance**: 64x64 voronoi with 20% walls, corner to corner: < 100 ms (spec SC-002) and re-plan after an obstacle < 50 ms (SC-007), asserted in `tests/integration/pathfindingPerformance.test.ts` (the wall clock is banned in `src/game`); unit tests assert optimality against an independent O(n^2) Dijkstra on 200 random square/voronoi maps.

### D-45 Needs, mood, utility AI and movement (task 2.4; `src/game/ai`)
- **Registration**: `registerAi(engine)` (called by the engine constructor, returns the `AiService`) adds the components `Needs`, `Mood`, `Health`, `Relationships`, the task types `move`, `ai.satisfy`, `ai.idle`, the behavior handlers `any_need_below_critical`, `satisfy_critical_need`, `idle_wander`, the slot-4 system `ai.needs`, the slot-5 system `ai.decision` and the query `needs-of {entityId}`; it also registers pathfinding. Humanoid prototypes carry `Needs` (every need at `needStartValue`), `Mood` (50000), `Health` (100000) and an empty `Relationships`; every humanoid now runs `basic_needs`. `Relationships` is the D-25 data model only (cap 16 entries, 8 history records); writers come with their causes.
- **Needs**: linear decay per tick = `combine(combine(decayPerTick, difficulty needDecayMultiplier), trait decayRateMultiplier)` (027 FR-014 combine, never below 1); thresholds and satisfaction are not scaled. The difficulty multiplier is a hook: `AiService.setNeedDecayMultiplier(fn | null)`, default the `needDecayMultiplier` of the game's difficulty mode (1000 for steady). Pack v0 decay: hunger and rest 0.15 per tick (critical at 20 after 400 ticks), the rest unchanged. Satisfaction by an item = authored amount combined with the trait `satisfactionBonusMultiplier`, clamped at 100; `need.item.consumed` is emitted per consumed item.
- **Consequences**: hunger at zero lowers `Health` by `starvationHealthPerTick` (0.25, so 400 ticks) from the same tick; at zero health `entity.died {cause: "Starvation"}` and `requestDelete` (`entity.deleted` at slot 17 carries the styled name). While no need is zero health recovers `healthRegenPerTick` (0.02). Exhaustion has no damage: a need at zero that is satisfied by sleeping makes the settler collapse (the `ai.satisfy` task gets priority `Collapse` 200, above every other task).
- **Mood** (permille units D-04): target = mean need level + active influences + trait `moodBonus`, clamped; mood moves a `moodSmoothing` (5%) share of the gap per tick, at least 1 unit. Influences (cap 8, expired dropped first, oldest evicted): `consumed_<need>` +3 for 72 ticks, `slept_on_ground` -4 for 144 ticks. Risk: `riskSuccessPermille` = D-04 formula, exposed with `rollRisk(stream, mood)` on `ai.risk`.
- **Utility** (D-25 numerics): `score = base + sum(factors)`, integers; candidates are the critical needs that have a plan; base = `(needCount - rank) * 1000` from the role-derived order, so the order dominates; factors `urgency` (0..999), `emergency` (+10000 when the need is 0) and `wealth_luxury` (+-300 for comfort/faith/social, wealth by coins held against `wealthyCoins` 500 / `poorCoins` 50). Ties go to the lowest need id; there is no randomness in the choice. Roles are derived, never stored: `sellsItems` prototype = Merchant (social > hunger > rest > safety), dominant skill `combat` = Guard (safety > rest > hunger > social), others Worker (hunger > rest > safety > social); a prototype `needPriority` overrides; the remaining needs follow in file order. New factors: `AiService.registerDecisionFactor`.
- **Streams**: `ai.decide` (idle: stand still or wander, and how long), `ai.wander` (target cell, uniform among cells reachable within `wanderRadiusCost` 60), `ai.risk` (D-25). Added to the stream registry of section 0.
- **Orchestration**: an entity with `AiState.treeId` and a `TaskQueue` is *due* at slot 5 when its queue is empty, or when every task is below priority `Need` (100) and one of its needs is critical (a critical need redirects a wandering or working settler within the tick). Priorities: idle 10, jobs by convention 50, need 100, collapse 200. Leaves that enqueue a task return `Success` at once (no tree memory is needed: the tree restarts when the queue is empty again); `idle_wander` is a no-op while any task exists, so an unsatisfiable critical need does not freeze the settler.
- **Satisfying a need** (`planNeed`): methods in authored order. `Item`: own inventory first (nothing to walk), then the finders registered with `AiService.registerNeedSource(finder)` (storage, stockpiles, markets plug in here; a finder returns a `NeedPlan` naming the holder entity and the cell to stand on, or null). `Furniture`: the nearest reachable entity of that prototype on the same map (path cost, ties lowest id). A need with a furniture method and no bed is satisfied **on the ground** where the settler stands at `groundSleepRate` (50%) of the authored amount, plus the `slept_on_ground` influence. `Zone` methods are not supported yet. No forage or well was added: the pack has no water need and the starting bread (every humanoid now carries 2) covers the first ~900 ticks; food production is Phase 3.
- **Movement**: task `move` `{mapId, target}`: A* from the pathfinding service, `progress += moveSpeed` per tick (10 = one normal cell; trait `speed_multiplier` for `ALL_WORK` scales it) and one cell is entered per `move cost` of progress (5..25), several per tick on fast ground. A blocked next cell re-plans (max 3, then `blocked`); no path = `unreachable`; other-map targets are `unreachable` until routes across links are followed. - **Content changes**: needs hunger/rest decay 0.15; peasants and carpenters carry 2 bread; new content constants `starvationHealthPerTick`, `healthRegenPerTick`, `moodSmoothing`, `groundSleepRate`, `sleepWakeThreshold` (90), `wealthyCoins`, `poorCoins`, `wanderRadiusCost`, `idleStandChance` (0.3), `idleStandMinTicks`/`idleStandMaxTicks` (6/24).

### D-46 Job boards and claiming (task 3.1 a, b, e; `src/game/jobs`)
- **Scope**: board data and lifecycle, claim algorithm, job type executor registry, pause sources, AI integration, one real job type (`fell.trees`). Town Crier fleet and `PostJob` delivery by criers (3.1c), content hooks for other job types (3.1d), stockpile-aware wood stock (3.2), recurrence and concurrency stay open. Postings are therefore **single-claimant and one-time** for now: `{id, boardId, jobTypeId, target{mapId,cellIndex,entityId|null,materialId|null}, priority 0..100, urgent, wage, posterFactionId, eligibility[], status Open|Claimed|Done|Failed|Cancelled, claimId, claimantId, createdTick, claimedTick, finishedTick, reason}`; `concurrency`, `slotsFree`, `recurrence`, `blocked`, `standingOrderId`, `deliverToZoneId`, `ownerSystem` of D-08 are added by the tasks that need them. Active postings live in the `JobBoard` component of the board entity (entities save section), the last 16 finished ones in its `history`. Ids: `nextPostingId`, `nextClaimId`.
- **Claim order**: D-08 stands: `(priority desc, urgent desc, familiarityBucket desc, pathCost asc, postingId asc)`; **there is no PRNG tie-break** (the plan text "PRNG ties from a named stream" is superseded by D-08), so the stream `jobs.claim` is not registered. `pathCost` is the path cost from the worker to the target cell.
- **Claiming**: a settler must stand at the board (017 FR-002). The behavior action `claim_job` (condition `jobs_available` first, both in the `basic_needs` tree between the critical-need branch and `run_tree idle_wander`) picks the nearest reachable board (path cost to the board cell, ties lowest entity id) that has a posting the worker could claim, and enqueues the task `jobboard.visit` at priority 50. On arrival the task claims the best posting (`claimPosting` checks and changes in one call; settlers act in ascending entity id, so racers never double claim; losers find nothing and decide again next tick) and enqueues the job's own task (type = job type id, priority 50, data `{postingId, claimId}`). `claim_job` fails when the entity already has a task of priority >= 50. A job type without a registered task handler is never offered.
- **Eligibility** (data, evaluated at claim time): `AdultHumanoid` = the worker has a `Citizen` component (there is no age model yet), `FactionMember{factionId}`, `NotHostileToPoster` (D-08 rule: member of the poster faction, or integer-truncated mean standing of the worker's factions toward the poster >= -30), `MinSkill{skillId, level}`, `TierUnlocked{tier}` (tier from `JobService.setTierSource`, default `hamlet`). Default for new postings: `[AdultHumanoid, NotHostileToPoster]`; poster faction default is the government faction.
- **Abandon and back-off**: a failed job step (unreachable target, walk failed) calls `releasePosting(..., backoff = true)`: the posting is `Open` again, `jobboard.job.abandoned` is queued and the same entity may not claim that posting for 144 ticks (back-offs saved in `systems.jobboard`, pruned when expired or the posting is gone). A task cancelled by priority (critical need), the player or a deleted worker releases without back-off, except `unreachable`. `target_invalid` (the target no longer fits, e.g. the tree is gone) fails the posting for good (`jobboard.job.failed`). A cancelled posting (`jobboard.job.cancelled`) makes the claimant's task fail with `posting_gone`. Events added to the section 4 catalogue: `jobboard.job.failed {boardId, postingId, jobTypeId, reason}`, `jobboard.job.cancelled` (same payload).
- **Pause**: two independent flags `pausedByPlayer` / `pausedBySystem` on the board; `jobboard.paused` / `.resumed {boardId, source: Player|System}` are queued when a flag changes. Paused boards offer nothing (postings may still be added); claimed jobs run to completion; resuming creates no backlog.
- **Wage and completion**: wage defaults to the job type's `wage` (`fell.trees` = 2). `completePosting` pays through `payWage`: wage 0 = nothing; a payer set with `JobService.setWagePayer` takes over (the treasury of 4.1); otherwise the coins are **minted into the worker's inventory** (only the player government will have a treasury; none exists yet); a full inventory leaves the wage unpaid with an engine warning. `jobboard.job.completed {boardId, postingId, claimId, jobTypeId, workerId, wage, outputs}`. The executing wrapper emits `skill.work.completed` once for the job type's `skillId` after completion (D-08).
- **Executor registry**: `registerJobType(engine, jobTypeId, JobExecutor{requires?, start, step, complete?})` registers a `TaskHandler` whose type is the job type id; `createWorkAtLocationExecutor(engine, {baseTicks, complete})` is the generic walk-then-work-for-`workDuration(content, worker, jobType, baseTicks)`-ticks executor. `complete` applies the effect and returns the outputs, or null for `target_invalid`.
- **Commands**: `SetJobBoardPaused {boardId, paused}` (player pause), `PostJob {boardId, jobTypeId, mapId, cellIndex, entityId?, materialId?, priority?, urgent?, wage?}` (user-managed boards only, `BoardNotUserManaged` otherwise; posts at once until the crier of 3.1c exists), `PostCustomJob` (same payload, any board, posts at once; used by tests, scripts and the player-job posting). Queries: `job-boards {}`, `jobs-on {boardId}`, `job {postingId}`. CLI verb `jobs [boardId]`.
- **`fell.trees` auto-poster** (system posting, goes to the board at once per D-08): every 12 ticks, while the oak log total over all inventories is < 40 and fewer than 4 felling postings are active, post the nearest forest cells (path cost <= 300 from the board; ties lowest cell) on each running board, never twice for one cell. Work: 24 base ticks, then the cell becomes the terrain its `clearsTo` names (grassland) and the worker gets oak_log x3 (as far as it fits). `jobs.json`: `fell.trees` wage 2. `job_board` engine prototype carries `JobBoard {}`.
- **Scenario**: `scenarios/first-jobs.json` (seed 42 Small, two days: postings done, logs and coins in inventories, save/load, replay). Seed 42 Small day 1: workers 3 to 8 each fell trees; the day-2 state hash is `86f50e627a2fe9d6` (same as the living-world scenario, both are the same run).

### D-47 Stockpiles, reservations and hauling (task 3.2; `src/game/storage`)
- **Scope**: the reservation primitive (D-09), `Furniture` / `Stockpile` entities, routing, `haul.deliver` with its auto-poster, stock queries, the storage need source and the storage decay hook. Zones do not exist yet (3.4), so the "stockpile" is a **furniture entity** carrying `Stockpile {priority 0..100 default 50, filter {categories[], materialIds[]}|null}` (the zone-level filter, tier 0 `deliverToZoneId` and tier 1 zone skill affinity of 018 FR-010 arrive with 3.4; `RouteTier` has the values 2 to 4). The `chest` engine prototype (`Position`, `Inventory` 16 slots / 200 kg, `Furniture {furnitureId}`, `Stockpile {}`) is the first furniture entity; construction (3.5) spawns furniture by the same prototype id. Worldgen puts one chest on the clearing after the settlers (entity 9 of a default seed-42 game). `Furniture` is `{furnitureId}` only; content records give tags, storage and effects.
- **Inventory scope**: no new flag. `queryable: false` (D-09, already in the component) hides an inventory; claimable storage is `Furniture + Inventory(queryable)` or `loose_pile`; `build_site`, citizens and creatures never count, so carried goods are not sources. No save shape changed (new sections `systems.reservations` and `systems.storage`, new components only), no migration.
- **ReservationService** (`systems.reservations`, ids from `nextReservationId`): `reserve` (exact, throws `InsufficientStock`), `reserveUpTo` (partial, null when nothing is free), `release`, `releaseHolder(holder, kind?)`, `releaseInventory`, `commit(id, destination|null)` (transfer with freshness, or consume; all or nothing), `availableTo(owner, material, requester)` (stock minus the others' reservations), `reservedQuantity`, `reconcile` (clamps to the stock, drops reservations of gone holders or inventories; every tick in slot 10). Deleting a holder or an inventory owner releases at once (before-delete hook). A `Haul` reservation whose holder has no `haul.deliver` task is released by the storage system. The AI hook `AiService.setItemAvailability` makes `consumeNeedItem` respect reservations when a settler eats from another entity.
- **Filters**: union of ids and categories, empty lists = no filter (D-26), `SetStorageMaterialFilter` replaces the own filter, validates categories and materials (`UnknownCategory`, `UnknownMaterial`), never evicts. New command `SetStockpilePriority {entityId, priority}` (`NotAStockpile`).
- **Routing order** (task text over the 018 wording where they differ): tier (2 matching own/default filter, 3 stockpile without filter, 4 other furniture storage; currency never tier 4) > stockpile priority desc > path cost asc > free capacity desc > entity id asc. Destination: same map, reachable, store permission (a "locked chest" is a chest whose rules deny the actor, D-09), filter accepts, room for a unit.
- **Hauling**: job type `haul.deliver` (content unchanged, wage 0, skill `hauling`). Posting target = source cell, `entityId` = source (loose pile, storage or a citizen holding goods), `materialId`; no quantity field (the hauler takes what it can carry of the unreserved stock). Hauler: reserve (`Haul`) -> walk to the source (re-targets a moved source up to 5 times) -> `commit` into its inventory -> `chooseRoute` -> walk -> `transfer` as much as fits, excluding a full storage and trying the next (3 reroutes) -> done. Goods nothing accepts stay with the hauler (completed job); the poster posts them again. Failure reasons `target_invalid`, `no_capacity`, `no_destination`, `source_gone`, `approach_failed`; cancel and failure release the reservation first. `JobExecutor` gained an optional `cancel` hook (called before the claim is released). Task phases `to-source` / `to-destination`, progress in the task record.
- **Poster** (system posting at once on the nearest running board, D-08; every 24 ticks, slot 10): loose goods = everything in a `loose_pile` plus units of **job outputs** (`jobs.json` `outputs`: oak logs, wheat) that a citizen carries and is not already delivering; personal belongings (bread, hammer, nails, coins) are never taken. Over-full or "mis-routed" stock inside storage is **not** evicted (FR-006 forbids it); production outputs of 3.3 post through `postHaulJob`. No destination -> `storage.no-compatible-destination {entityId, materialId, quantity}` once per holder and material (marks in `systems.storage`, cleared when the goods are gone or placed), `NoStorageDestination` reporting is for 3.6. Open haul postings whose goods or destination vanished are cancelled; emptied piles are deleted.
- **`fell.trees`** is unchanged: logs go into the feller's inventory and the poster has them hauled to the chest. The wood stock rule (below 40 logs over all inventories) still counts chest and carried logs. A default chest holds 40 oak logs (200 kg), then the settlers keep the rest and `no-compatible-destination` fires once per holder.
- **Decay**: `inventory.decay` (slot 3) asks `StorageService.decayModifierMilli(entity)` per entity: the product (`combineMilli`) of the furniture content's `inventory.decay.rate` effects and registered `addDecayModifierSource` sources (Pantry of 3.4); difficulty multiplies on top (D-07). 0 = never expires, 500 = half speed, non-perishables unaffected.
- **Need source**: settlers whose `Item` need is not met by their own inventory walk to the nearest reachable storage that holds the item (ties lowest id, others' reservations excluded) and eat there.
- **Queries / CLI**: `stock {materialId?}` (overview with slots and per-material totals, or one material with total, reserved, available, free and holders), `stockpiles {}`, `reservations {}`; CLI verb `stock [materialId]`. Catalogue: command `SetStockpilePriority` added.
- **Scenario / goldens**: `scenarios/hauling.json` (seed 42 Small, two days, logs in the chest, save/load, replay). The new chest changes entity ids after 8 (demo peasants start at 10), the entity total (8 -> 9) and the golden ASCII world map.

The derived fields are saved but never trusted: the load rebuilds them from the world, silently (D-11).

Gap order: `TooSmall`, `NotEnclosed`, one `MissingFurniture` per unmet requirement (text `2x id:crate or 2x id:chest`, closest alternative's `required`/`present`), `MissingJobBoard`.
- **Timing**: commands only change tiles; slot 9 re-derives all zones every tick (cost is O(tiles) occupant lookups, ~2 ms for 200 zones), so status and events appear in the tick of the change; effects need `tickCount > activeSinceTick`. `isInActiveZoneOfType(engine, mapId, cell, typeId)` is the room restriction query for 014 (D-10) and has the same one-tick delay.
- **Grammar**: the typed predicate is D-11's `FurnitureRequirement`, extended with an optional density `perTiles` (`count x ceil(tiles / perTiles)` pieces, at least one group). Text form: `any bed`, `2x tag:chair`, `id:table`, `A or B`, `A and B` (and binds loosest), `1x tag:bed per 8 tiles`; invalid text throws `ZoneError InvalidRequirement`. Content: `furnitureRequirements[][]` of `{kind: id|tag, ref, count, perTiles?}` plus `requiresJobBoard` (default false); schema and reference checks at load reject zero counts, unknown kinds, unknown furniture ids and tags.
- **Designation details**: `AddZoneTiles` cells that do not touch the zone become zones of their own (same type, same filter); an emptied zone is deleted; `reassign` removes the cells from the other zones first (which may split them). The locked tier uses the job service tier source (`ContentLocked`).
- **Merge details**: detection compares the walls around each zone with the previous pass (runtime memory, rebuilt silently on load): a wall cell that stopped enclosing and is next to another zone of the same type offers a merge once per pair (survivor = lower id). `MergeOffer` is saved with the tile counts of both zones; an offer lapses when either zone is gone or changed size. On accept the free cells that touch both zones (not walls) join the survivor; if the result is not contiguous the confirm fails as a lapsed offer.

Furniture in a `stockpile` zone is a stockpile even without the `Stockpile` component; furniture in a `dwelling` zone is excluded from every tier.
- **Boards**: a `job_board` entity on a tile of a non-active zone gets `PauseSource.System`; lifted when the zone is active or deleted. The set of boards paused by zones is saved in `systems.zones.pausedBoards` so unrelated system pauses are untouched.

Save: new component `Zone` and section `systems.zones {mergeOffers, pausedBoards}`; the state hash of every game changes (new section), no migration needed (`defaultForOlderSaves`).
- **Scenario**: `scenarios/zones.json` (seed 42 Small: stockpile zone around the starting chest, cells 255-258, zone id 10, active the tick after the command is queued).

### D-49 Production and crafting (task 3.3; `src/game/production`)
- **Scope**: the order model, the `craft.produce` executor, the poster, output hauling, the cancel rules of D-10, blocked-reason reporting for 025 (`explainOrder`, `explainWorkstation`), the commands of section 3.5, the queries `production-orders {workstationId?}`, `order {orderId}` (order plus `blocked[]`), `recipes-for {workstationId}`, `workstations {}`, the CLI verbs `orders` / `order ...` and the workstation prototypes. Variants and chains stay as D-10 says (separate recipes; chains through orders).
- **Workstation = furniture entity** with the component `ProductionOrders {orders[], craft|null}` (D-10) next to `Furniture`, `Position` and an `Inventory` (12 slots, 200 kg, `queryable: false`: waiting inputs are no stock and no routing destination). Prototypes `oven`, `grinding_mill`, `sawmill`, `workbench` (id = furniture id, like `chest`); construction (3.5) spawns them by the same ids. Recipe compatibility = the recipe's `workstationTag` is one of the furniture tags. Order of 026: standing orders call `createProductionOrder` and `capableWorkstations`; this module has no "keep N in stock".
- **Order**: `{orderId, workstationId, recipeId, quantity, remaining, priority 0..100, status Active|Paused|Completed|Cancelled, postingId|null, createdTick}`; `quantity` = number of crafts; at most 16 finished orders per workstation are kept. `CreateProductionOrder` without `workstationId` picks the capable workstation with the fewest unfinished orders (lowest id on ties); no capable one = `RecipeNotCompatible`.
- **Posting**: slot 8, every 6 ticks, per workstation that is not crafting and has no posting out: the highest-priority active order with no blocker (`orderBlockers` empty) gets one single-craft `craft.produce` posting (target = workstation cell + entity, priority of the order, eligibility default plus `MinSkill` when the recipe has `minSkillLevel`) on the nearest running board (D-08). One posting = one crafter = at most one craft at a time per workstation (014 FR-012). The posting maps back to its order by `order.postingId` (the posting model has no `ownerSystem` yet).
- **Crafting**: the crafter fetches what the work inventory lacks (inputs and one unit of each tool) from claimable storage (`findSources`, nearest first, no reservation while walking, all or nothing per source: a lost race fails the claim with `missing_input` and the usual 144-tick back-off), deposits it, then **locks** inputs (`Lock`) and tools (`Tool`) on the work inventory (014 FR-013), fixes `workDuration` and waits a serialized tick wait. Completion consumes the locks (tools are released), places the outputs in the work inventory plus the `rollOutputBonus` (stream `skill.output`) extra units on the first output (extras that do not fit are not made), emits `skill.work.completed` for the recipe skill and `production.crafting.completed` with the actual quantities. Outputs that do not fit (checked on a copy, inputs leaving first) make the crafter wait with `production.output.blocked` once, retried every 6 ticks. Recipe durations are at least 1 (schema), so "0-duration in the same step" is moot. `OutputDestination` is not modelled: outputs always go to the workstation and `postOutputHauls` posts `haul.deliver` (through `postHaulJob`) for everything in a work inventory that no unfinished order needs (inputs or tools), routed per 018.
- **Cancel rules** (the exact D-10 split): `CancelProductionOrder` = status `Cancelled`, an open posting is cancelled, a claimed craft that has **started finishes** (outputs made, `remaining` counts down, the order stays `Cancelled`), a claimed job still fetching is stopped (task cancelled, carried goods go back to the workstation, posting cancelled). `SetProductionOrderPaused` withdraws the posting the same way. `CancelCraft {workstationId}` = interrupt: locks released, nothing consumed, progress gone, `production.crafting.interrupted {reason: player_cancel}`, the claim goes back to the board (open again, no back-off) and the order continues; the crafter's task stops at its next slot-6 turn. A critical need interrupts identically (reason of the cancel token); `sweepStaleCrafts` (every tick) interrupts crafts whose crafter was deleted (`crafter_lost`), whose posting vanished or was taken (`posting_gone`) or whose task is gone. A deleted workstation cancels its unfinished orders, interrupts its craft and drops the work inventory as a `loose_pile` on its cell. Invariant (tested over 500 ticks): per material, all inventories together = start + produced - consumed.
- **Recipe schema addition**: `minSkillLevel` (0..100, default 0) next to `roomZoneId` (active zone of that type, `isInActiveZoneOfType`) and `toolMaterialIds`. Tier lock = `unlockTier` against the job service tier.
- **Tier source default**: until the tier system of 5.x calls `JobService.setTierSource`, the tier in force is the `startingTier` game option (it was always `hamlet`); the bakery scenario starts at `village`.
- **Blocked reasons (025)**: `explainOrder(engine, orderId)` returns `{orderId, workstationId, status, reasons[]}`, `explainWorkstation(engine, workstationId)` the reasons of a workstation (`NoOrders` = Idle; empty while crafting or served); a reason is `{kind, params, causeRef}` with the 025 names and params: `Paused{productionOrderId}`, `LockedByTier{contentKind, contentId, requiredTier}`, `MissingWorkstation{workstationTag}`, `MissingRoom{zoneTypeId}` (causeRef zone of the cell, when there is one), `NoQualifiedWorker{skillId, requiredLevel}` (no citizen has the level, or no citizen at all), `MissingTool{tag}` (tag = tool material id), `MissingInput{materialId, required, available, noProducer}` (available = unreserved work inventory + unreserved claimable stock; causeRef = the workstation of the first producer order that is not served, null when a producer is served, `noProducer` when none exists, producers = active orders whose recipe outputs the material, plus job types listing it as an output with an active posting), `OutputBlocked{materialId}`. Order of the list: Paused, LockedByTier, MissingWorkstation, MissingRoom, NoQualifiedWorker, MissingTool, MissingInput (recipe order), OutputBlocked, NoOrders. Pure and derived on demand; no state. 025 registers a `Workstation` provider that calls `explainWorkstation` and a `ProductionOrder` view over `explainOrder`.
- **Events** as section 4.4: `production.order.created|completed|cancelled`, `production.crafting.started|completed|interrupted`, `production.output.blocked`; `.failed` stays reserved (nothing hard-fails: a vanished recipe or station fails the *posting* with `target_invalid`).
- **Scenario step `debugSpawn`** (scenario/test only): `{debugSpawn: {prototypeId, mapId, cells[], overrides?, inventory?}}` dispatches the queued command `DebugSpawn`, which only `createScenarioSession` registers (the default session of `runScenario` and the CLI `--script`); real sessions answer "unknown command". It is logged and replays. `scenarios/bakery.json` uses it to build the room, workstations and stock that construction (3.5) and gathering (Phase 5) will provide.
- **Not done** (no consumer yet): hand-crafting without a workstation, quality, `OutputDestination`, a zone requirement that makes an oven count only inside a bakery, crafts that fetch from the carried stock of other citizens.

### D-50 Construction (task 3.5; `src/game/construction`)
- **Scope**: blueprints as `build_site` entities, `validatePlacement`, the supply and build jobs, completion, cancel and deconstruction, wall obstruction, the commands of section 3.3 plus player-facing aliases, queries, CLI verbs `build` / `sites`. Details: D-27 stays valid; this entry fills what it left open.
- **Job = site**: the `jobId` of every section 3.3 command and 4.4 event is the entity id of the `build_site` (a deconstruction gets a site as well, on the building's cell). Component `BuildSite {kind Construction|Deconstruction, prototypeId, status Planned|Supplying|Building, required[], progress, durationTicks, builderId, startedTick, supplierId, postingId, priority, urgent, paused, blockedMaterialId, targetEntityId, ownerFactionId, createdTick}`; the delivered materials are the site's own `Inventory` (`queryable: false`, so storage queries and the haul poster ignore it). `Done` and `Cancelled` exist only in the history `systems.construction.recent` (kept 288 ticks, shown by `construction-queue`). Engine prototype `build_site` added.
- **Build definition = furniture record** (022 furniture table, `wall` and `door` included): new fields `constructionTicks` (default 24), `deconstructionYield` (default none), `removable` (default true) next to `constructionMaterials` and `unlockTier`; unlock check = job service tier source (until 4.4 the `startingTier` option). No `unlockTier` means `hamlet`. v0 values: bed, workbench, chest, table, sawmill, wall, door at `hamlet`, oven at `village`; wall 2 stone_block, door 2 oak_plank + 2 nails.
- **Commands** (queued, mode default): `QueueConstruction {prototypeId, mapId, cellIndex, priority?, urgent?}`, `QueueWalls {prototypeId: wall|door, mapId, cells[], priority?}`, `QueueDeconstruction {targetEntityId, priority?}`, `CancelConstructionJob {jobId}`, `SetConstructionJobPaused`, `SetConstructionPriority`, `MoveConstructionJobToFront` (priority 100 + urgent); aliases for the renderer: `PlaceFurniture {furnitureId, mapId, cell, priority?}`, `PlaceWall {mapId, cells[]}`, `PlaceDoor {mapId, cell}`, `CancelConstruction {jobId}`. Errors as section 3.3 (`ConstructionError`).
- **Placement validation** (`validatePlacement(engine, prototypeId, mapId, cellIndex)`, query `validate-placement`): reasons `UnknownMap`, `OutOfBounds`, `UnknownPrototype`, `TierLocked {unlockTier}` (text `Unlocks at <Tier>`), `TerrainNotBuildable` (content `buildable`), `SiteExists`, `Occupied` (furniture, wall, door, job board); all reasons are returned, `valid` = none. Citizens never block (spec 004). Zone membership is **soft** (spec 024 edge case): the result carries `zoneId`, never a reason. Command errors: first reason decides (`OutOfBounds`, `UnknownPrototype`, `ContentLocked`, `LocationBlocked`, `LocationAlreadyOccupied`). Query `build-menu` lists definitions with `locked` and `Unlocks at <Tier>`.
- **Routing and jobs**: system postings go at once to the nearest running board (D-08). Job type `build.supply` (new, skill `hauling`) carries materials; `build.construct` (existing, skill `construction`) builds. The poster runs in slot 8 every 6 ticks: one open posting per site, so one supplier or one builder per site (FR-012, no double claim), supply postings for the first missing material that has a source. Eligibility = `defaultEligibility()`. `ReservationKind.Supply` added: the supplier reserves at the source, commits into its own inventory, deposits at most what the site still needs; leftovers and goods of a cancelled trip become a `loose_pile` where the supplier stands.
- **Work**: duration fixed at start = `workDuration(construction skill, constructionTicks)`; deconstruction `max(1, floor(ticks / 2))` (D-27); `progress` = `tick - startedTick`; `skill.work.completed` comes from the job wrapper once per completed claim. Tools are **not** required (the job type's `toolMaterialId` is unused until the tool mechanic of a later task). A wall that is taken down is worked from its first traversable neighbour cell (the posting target).
- **Completion**: spawns the engine prototype named like the definition (`oven`, `chest`, `wall`, `door` ...) or `furniture_piece` + `Furniture {furnitureId}` (bed, table); a wall sets `BlockReason.Wall` at once; the site entity is deleted; `construction.job.completed` gets one extra field `entityId` (the placed entity, null for a deconstruction). A cell taken meanwhile (or a vanished deconstruction target) makes the sweep cancel the job with `location_lost`.

Zone evaluation does not count the obstruction of a wall that is flagged for deletion (the flush runs after slot 9).
- **Suspension**: a site with no source for any missing material sets `blockedMaterialId`, emits `construction.job.suspended {jobId, reason {kind MissingInput, params {materialId, required, delivered, available}}}` once and `construction.job.resumed` when a posting is possible again; `siteBlockers` (for 025) also reports `Paused` and `LockedByTier`.
- **Content tests adjusted**: the production integration test builds its bakery with a door (walls now obstruct); `workAtLocation.test` uses its own `test.work` job type (every real job type has an executor now).
- **Scenario**: `scenarios/build-bakery.json` (stone, planks and nails from a `debugSpawn` chest: the chain log, sawmill, planks, smithy, nails needs content of later tasks). About 700 ticks for 8 jobs with the six starting settlers.
- **Not done**: tool requirement, `NoQualifiedWorker`, multi-cell buildings, rectangle expansion (the renderer expands rectangles to cells), reorder beyond priority/urgent.

### D-51 Status explanations and production flow (task 3.6; `src/game/status`)
- **Scope**: derivation providers for the subject kinds that exist after 3.5 (`Citizen`, `Workstation`, `ProductionOrder`, `ConstructionSite`, `Zone`, `JobBoard`, `JobPosting`, `LoosePile`), `explain` with cause chains, the settle tracker and the `status.blocked` / `status.unblocked` events (D-18), the Idle & Blocked list, the flow ledger, the queries `explain {id, kind?}`, `idle-blocked {includeUnsettled?, state?, kind?}`, `flow {}`, `flow-of {materialId}` and the CLI verbs `why`, `idle`, `flow`. No commands. `StandingOrder` (4.3) and `Dwelling` (4.5) are enum members without a provider; they register theirs with `getStatusService(engine).registerProvider`. Reasons of 026/029 that the spec lists (`NoSeatOfGovernment`, `NoSteward`, `ScopeZoneMissing`, `AwaitingTownCrier`, `NoHouseholdStorage`, `DwellingRequirementsUnmet`, `LocationBlocked`) are in the enum and in the precedence list; their owners fill them.
- **Provider interface** (D-18 made concrete): `StatusProvider {kind, subjects(engine): StatusSubjectRef[], evaluate(engine, ref, context): SubjectStatus | null}` with `SubjectStatus {state, activity | null, reasons[]}`; one provider per kind; pure. D-18 wrote `reasons(ref, ctx)`; `evaluate` returns state and activity too because the state is not derivable from the reasons alone (a citizen with a task has no reason at all and still needs "working on X").
- **Ref shape**: `StatusSubjectRef = {kind, id}` (one `id`: entity id; posting id for `JobPosting`; order id for `ProductionOrder`/`StandingOrder`), instead of the spec's `{kind, entityId, postingId?}` / `{kind, orderId}`. Production's `CauseRef {zone|workstation, entityId}` is mapped by the provider (`fromProductionCause`). `ProductionOrder` is an extra kind (D-49 announced the view).
- **Two additions to `BlockedReasonKind`** (the 23 of spec 025 stay in FR-004 order): `AwaitingDecision {boardId}` (an idle citizen has a posting it could claim but has not walked to the board yet; it decides when its idle task ends, at most one idle wait) and `Unexplained {}` (fallback of `evaluateSubject` for a non-Active subject whose provider returned no reason; never silent; the soak tests assert it never occurs). Reasons that `AwaitingWorker {postingId}` points at the posting as `causeRef` (spec: `postingRef`), and a posting nobody takes is explained by the posting subject itself.
- **Citizen**: Active when its top-level task is a claimed job, `ai.satisfy` (sleep = `Sleeping`, else `Eating`) or `jobboard.visit` (`WalkingToBoard`); Idle otherwise (empty queue, wandering, standing) with reasons derived the way `claim_job` fails. A crafter whose outputs do not fit is not reported on the crafter (the workstation/order show `OutputBlocked` when idle); the spec's "waiting at a workstation" edge case is not modelled.
- **State of non-citizens**: workstation `NoOrders` = Idle, everything else non-Active = Blocked. An order or workstation whose craft job is posted and still open is Blocked with `AwaitingWorker`; a build site likewise; a loose pile whose haul posting is open likewise; an open posting is Blocked (`Paused` with the board as cause, `NoQualifiedWorker`, `Unreachable`, else `AwaitingWorker`). These show in the Idle & Blocked list only after the grace period.
- **Settle tracker** (root section `statuses`, D-18 plus): `{subject, state, reason, sinceTick, reasonSinceTick, stallStart, pendingKey, pendingSince}`. Identity of a primary reason for "changed" = kind plus the first identifying param (`materialId`, `zoneTypeId`, `workstationTag`, `tag`, `jobBoardId`, `zoneId`, `postingId`, `boardId`, `productionOrderId`, `entityId`); counters never re-emit. `sinceTick` = first tick of the continuous stall (kept when the primary changes inside it); `reasonSinceTick` = first tick of the current primary. Immediate kinds: `Paused`, `NoSeatOfGovernment`, `NoSteward`, `LockedByTier`, `ScopeZoneMissing`, `NoOrders`. Becoming Active publishes at once. The pass runs every tick at slot 18 (spec FR-008); a subject that disappears emits `status.unblocked {removed: true}` if it was published as non-Active; after a load, records of vanished subjects are dropped silently.
- **Idle & Blocked view**: live reasons, `sinceTick` from the tracker, `settled` = the tracker published this state; default list = settled only (`includeUnsettled` adds the settling ones), sorted by `sinceTick`, subject kind, id.
- **Flow ledger** (root section `productionLedger`): per day, entries keyed `(materialId, direction, source, subject)` with a quantity; `subject` is the workstation, build site, citizen, dwelling or null (spoilage in a storage that is no subject). Fed by the existing events (no producer-side hooks were missing): `production.crafting.completed`, `construction.job.completed` (`consumed`, `yield`), `jobboard.job.completed` (only job types whose content lists `outputs`; `haul.deliver` reports moved goods as outputs and `craft.produce`/`build.*` are counted elsewhere), `need.item.consumed`, `inventory.item.expired`, `housing.goods.consumed`; trade calls `recordFlow` (4.1). ### D-52 Gathering and farming (task 3.7a; `src/game/gathering`)
- **Scope**: closes the gap between D-15 (crops, gathering outputs) and the economy loop: crop plots, the four gathering executors and their auto-posters. Everything is headless; the player's only input is `DesignateZone` of a `farm_field`.
- **Crop plots** (system section `systems.gathering`): only cells of an Active `farm_field` zone that are `fertile_soil` can hold a crop; a plot is stored only while `Sown` or `Ripe` (`{mapId, cellIndex, materialId, stage, growthMilli}`), a fertile cell without a plot is `Fallow`. Zone tiles of other terrain are simply not crop cells. The crop is the first `cropOutputs` material of the zone type (wheat). Plots of cells that left the field (zone deleted, tile removed, terrain changed) are dropped; growth pauses while the zone is not working (active and past its activation tick, D-11).
- **Seeds**: none (D-15 stands): `farm.sow` is free sowing (no seed material exists in the pack, and wheat is the only crop, so a seed fraction of the harvest would make the first sowing impossible). A later crop that needs seed adds a material and a `seedMaterialId` on the zone type.
- **Growth**: every crop takes `cropGrowthTicks` (864, one constant for all crops; a per-crop value waits until a second crop exists). Growth is counted in milli-ticks; each tick adds `1000 * seasonModifier() / 1000`. **There is no season system in v1**: `seasonModifier()` is the hook (always 1000 = normal) where a calendar would slow growth. The slot-12 system `gathering` runs the crop pass; `gathering.crop.ripened {mapId, cellIndex, materialId}` is emitted when a plot ripens.
- **Jobs**: `farm.sow` (fallow to sown, 12 base ticks) and `farm.harvest` (ripe to fallow, 18 base ticks) work at the cell with `createWorkAtLocationExecutor`; a harvest gives the zone's `cropOutputs` (wheat x4) plus the farming output bonus (`rollOutputBonus` on the first output, `skill.output` stream) into the worker's inventory; the haul poster then takes the wheat to a stockpile. A cell that stopped being a working field cell, is not fallow (sow) or not ripe (harvest) fails the posting with `target_invalid`. `skill.work.completed` comes from `registerJobType` as for every job. `farm.tend` stays an executor-less content job (no engine effect, D-15) and is the job type that tests use for custom executors.
- **Deposits**: `mine.ore` (`iron_ore_deposit`, iron_ore x2, 36 base ticks, skill `mining`) and `quarry.stone` (`stone_deposit`, limestone x2, 30 ticks, skill `masonry`). Mining is finite: a deposit cell has `oreDepositCharges` (6) / `stoneDepositCharges` (8) charges (content constants); each completed job uses one charge and gives the job's `outputs` plus the output bonus; the charges left of a partly worked cell are stored in the gathering section (an untouched cell has no record); the last charge turns the cell into the terrain the deposit `clearsTo` (`cave_floor`, new content field values) and emits `gathering.deposit.depleted`. New skill `mining` (output bonus 0.5, like farming's) because no existing skill fits.
- **Auto-posters** (slot 12, every 12 ticks, system postings to the board at once, D-08): one shared poster (`postCellJobs`): per running board in ascending id, the candidate cells nearest to the board (path cost <= 400, ties lowest cell), never a cell that already has an active posting of the type, at most 4 active postings per type (2 for `mine.ore` and for `quarry.stone`, so a few miners leave the rest to haul and craft). Farm jobs are not stock-gated (a ripe crop is always worth harvesting). `mine.ore` posts only while the total iron ore in all inventories is below `oreLowStock` (8), `quarry.stone` while limestone is below `stoneLowStock` (12): carried and piled goods count, so waiting for a haul counts as produced.
- **Status**: the Zone provider asks `fieldReasons` for an Active `farm_field`: `LocationBlocked {zoneId, zoneTypeId}` (no fertile tile, Blocked) or `AwaitingWorker {postingId}` with the lowest open sow/harvest posting of the field as cause (Blocked; the posting provider then explains why nobody claims it, e.g. `NoQualifiedWorker`). A field with nothing open is Active. This uses the D-51 rule "everything non-Active except `NoOrders` is Blocked".
- **Query / verb**: `crops {zoneId?}` (every fertile cell of the field zones: stage `Fallow|Sown|Ripe`, growth permille, ticks to ripe at normal speed) and the CLI verb `fields [zoneId]`; no commands.
- **Existing tests adjusted**: the new auto-posters make settlers mine and quarry from the first hour, so `hauling.json` no longer asserts the first stockpile content is oak logs, `bakery.json` needs only 4 of its 8 bread in storage (settlers eat some), `firstJobs` counts the wages of all gathering jobs, the repl action pattern accepts `mine.ore (approach)`, query/skill/job-type counts and the verb group count grew by one. The world has no food loop yet: settlers starve after about five days (no bakery, wheat is not eaten), which is the job of the content tasks (5.x) and Checkpoint C.
- **Scenarios**: `scenarios/farming.json` (a `farm_field` over three fertile village cells, wheat in the chest after five days, farming XP, save/load mid-growth, replay) and `scenarios/mining.json` (two days of ore and limestone into chests).

### D-53 Town Crier fleet and player job posting (task 3.1 c, d; `src/game/crier`)
- **Scope**: D-08/D-12 for player-edited postings. Systems still post at once and never use a crier; construction and production commands are system postings (D-08) and do not wait for one. Only `PostJob`, `RemovePosting` and `ModifyPosting` on a user-managed board go through a crier. Steward origin, Notice Post and Bell Tower delivery (`DeliveryMethod` values exist), the Steward-cannot-be-crier rule and `NoSeatOfGovernment` belong to 4.3 (no Throne Room exists yet; a crier starts from wherever it stands).
- **State**: `TownCrier {status Available|Traveling, boardQueue, carrying}` component on a citizen (D-12). Pending updates `{updateId, boardId, changes[], origin, createdTick, crierId, dispatchedTick, startCost}` live in their **own** save section `systems.towncrier` with `nextUpdateId` (amends D-12, which put them in `systems.jobboard`: the crier folder owns them and `jobs` never imports it). A command makes one update with one change (`Add` / `Remove` / `Modify`); a crier carries all waiting updates of one board per trip.
- **Dispatch** (slot 7, system `towncrier`, after `jobboard`): every tick `recoverCriers` then `dispatchCriers`. Waiting updates are grouped by board (oldest first); the free crier with the cheapest path cost (ties lowest id) takes them all, becomes `Traveling` and gets the task `towncrier.deliver` at **priority 80** (jobs 50, critical need 100; D-45). A walking crier takes nothing more: later changes wait for the next free one (finite fleet, spec 017 FR-012). No crier at all: updates wait (`pending-updates.waitingFor = NoTownCrier`, board status `AwaitingTownCrier`). A crier without a delivery behaves like any settler.
- **Travel**: the task walks with a `move` child; time = path cost at the crier's move speed (`ceil(cost / 10)` ticks at normal speed; the `pending-updates` view gives ETA, remaining cost, progress permille from the crier's current position). A critical need interrupts the walk; `recoverCriers` re-enqueues it, the load is kept.
- **Apply**: on arrival `applyBoardUpdate` runs the changes through `postJob` / `cancelPosting` / `modifyPosting` (new: priority and wage only) and queues `jobboard.update.applied {updateId, boardId, via: TownCrier}`. A change that no longer fits (the posting finished meanwhile) abandons the update with `change_rejected`. Command-time checks (user-managed board, `UnknownJobType`, `ContentLocked`, `InvalidTarget`, `UnknownPosting`) reject at once; `validatePostable` is shared with `postJob`.
- **Cancel / loss**: `CancelPendingBoardUpdate {updateId}` removes the update (`jobboard.update.abandoned` reason `cancelled_by_player`); a crier left with nothing is available again and its walk is cancelled (US6.5). A deleted board abandons its updates at once (`board_gone`; simplification of US6.4: the crier does not walk to the empty spot). A deleted crier loses what it carried (`crier_lost`), waiting updates survive. `DismissTownCrier` returns the load to the queue.
- **Commands / queries / verbs**: `PostJob {boardId, jobTypeId, mapId, cellIndex, entityId?, materialId?, priority?, urgent?, wage?}` -> `{updateId}` (moved out of `jobs`), `RemovePosting {boardId, postingId}`, `ModifyPosting {boardId, postingId, priority?, wage?}`, `CancelPendingBoardUpdate {updateId}`, `AppointTownCrier` / `DismissTownCrier {entityId}` (`IneligibleCrier` unless a citizen on a map); queries `pending-updates {}`, `town-criers {}`; CLI verbs `post`, `unpost`, `pending [cancel <id>]`, `crier [appoint|dismiss <id>]`. `PostCustomJob` stays immediate (tests, scripts).
- **Starting kit**: the village board is **user-managed** (the town square; D-08: mode only says who may edit, systems post to it regardless) and the first peasant (entity 7 of a default game) is the Town Crier (D-06, D-12). Events added to the catalogue use the names that were already listed (`jobboard.update.queued/applied/abandoned`, `towncrier.dispatched`).
- **3.1d content hooks**: every job type of the v0 pack that goes on boards has an executor (`fell.trees`, `farm.sow`, `farm.harvest`, `mine.ore`, `quarry.stone`, `haul.deliver`, `craft.produce`, `build.supply`, `build.construct`) except `farm.tend`, which is explicitly deferred (`jobs/jobCoverage.ts`; the crop model of D-52 has no tending step). A test pins that nothing else is missing.

### D-55 Trade, treasury and traders (task 4.1; `src/game/trade`)
- **Scope**: spec 019 plus the owner's refined-credit rule (D-13), as far as the player can use it. Settlers' own buying (AI `trade.approach`, D-12 geography) and the AI-initiated offers are **not** built: trade is player-commanded through orders (the trade-policy screen stays descoped). `ProposeTrade` exists for scripts, tests and later AI; it runs the full protocol of D-12 without geography.
- **Treasury (amends D-12 "Throne Room containers")**: there is no Throne Room yet (4.3/4.4), so the treasury is the **inventory of the government faction entity** (`government_faction` prototype gets `Inventory {slotCount 8, queryable false}`; a save from before trade gets it added at load). New games start with the content constant `startingTreasury` = **1000** coins (Checkpoint C pays about 4 coins a day in wages; the old behaviour of minting is gone). The wage payer `JobService.setWagePayer(payWageFromTreasury)` pays from it: wage 0 nothing; short treasury or full worker inventory queue a `PendingWage` keyed by the claim id in `systems.treasury` (`treasury.payment.deferred`), retried every tick in id order, a smaller wage may pass a larger one that waits, a deleted worker's wage is dropped, `treasury.payment.completed` when paid; no government entity: `treasury.unavailable` once per day. `receiveRent(engine, dwellingId, coins)` is the rent hook of 4.5 (`treasury.rent.received`). Commands that spend coins take them from the treasury only through a settler's purse (below).
- **Prices (amends D-12 steps 2 and 4)**: `value` is the plain `valueMilli`. A seller asks `ceilDiv(sum(valueMilli x qty x scarcity) x multiplier x (1000 + margin), 1e6)` milli-coins and settles to `ceilDiv(.., 1000)` coins. `multiplier = floor(floor(priceMultiplier x agreement / 1000) x 1000 / 1000)` with `agreement = agreementDiscount` (**0.9**, content constant) while the standing entry between the trader faction and the settlement (either direction) has `tradeAgreement`, else 1.0; `scarcity` applies to a trader's own stock only: `1000 + floor(scarcityMaxPremium x (target - held) / target)` with `target` the quantity of its `sells` entry (0.2 max, so 1.0 to 1.2), never to refined goods or goods it does not restock; `margin = minimumMarginRate (content default defaultMinimumMarginRate 0.1, or the entity's Merchant value) + marginAddPermille(seller)` (Greedy +50). Barter goods are valued at plain `valueMilli` (D-12 reading kept). Counter coins = `ceilDiv(asked - barterMilli, 1000)`. Spec worked examples are a test table (base 5 x 2 -> 11, 1.5 -> 17).
- **Traders bid** (the settlement sells to a trader): the trader is the *buyer* in the protocol, the settler at hand the seller (so a Greedy settler asks more). The trader opens at `buyOfferPermille` (1.15) of the plain value rounded down, and re-proposes up to `buyCeilingPermille` (1.25, rounded up) of the value when countered; beyond that the negotiation ends `price-too-high`. Both numbers are content on the trader prototype.
- **Negotiation machine**: as D-12 (offers processed in ascending id at slot 10; accept executes in the same step; countered offers wait for the buyer; `AcceptTradeCounter {offerId}` starts round + 1 at the countered coins, beyond `maxNegotiationRounds` (3) the offer expires with reason `rounds-exhausted`; offers expire after `offerTimeoutTicks` (24); a standing change that makes the trader faction hostile cancels its offers with `faction-hostile`; a deleted party cancels with `buyer-deleted` / `seller-deleted`). Extra refusal reasons: `insufficient-funds` (buyer cannot pay what it offers), `not-wanted` (a buying trader does not want the goods), `not-for-sale` (the seller of a `ProposeTrade` has no `sellsItems`; the settlers' own jobs skip this check), `price-too-high`. Detail `refined-credit-exhausted` on `insufficient-stock` for a refined good. Offers get ids from `nextOfferId` in `systems.trade` (the root counter list of D-05 is not extended).
- **Atomic execution** (`executeTrade`): `Payment` reservations (holder: the buyer) on every leg's source, then `commit` leg by leg; on any failure the done legs are transferred back and the reservations released (`trade.execution.failed` with `buyer-inventory-full`, `seller-inventory-full`, `stock-changed`, `buyer-deleted`, `seller-deleted`). A completed trade records `FlowSource.Trade` flows (goods only, only when exactly one party is the settlement: the treasury or a citizen of the government faction), applies the standing hook and queues `trade.completed`.
- **Ledger (D-13 as the owner decided)**: content `refines: [{rawMaterialId, refinedMaterialId, ratioMilli}]` on the `Trader` component of the prototype (`trader_caravan`: iron_ore -> iron_ingot, 500). `credit[refined] += qty x ratioMilli` happens in `settleTrade`, i.e. at the moment the sale is settled. Stored per `(trader prototype, settlement faction, refined material)` in `systems.trade.ledger` (integer milli-items, no expiry, no decay, survives departure and save/load). A purchase of a refined good needs `qty x 1000 <= credit` (`TradeBuy` is refused with `RefinedCreditExhausted`, an offer with `insufficient-stock` + `refined-credit-exhausted`) and draws `qty x 1000` down. The trader's stash of the refined good is topped up to `floor(credit / 1000)` on arrival and every tick (so a returning caravan brings the same stock; the refined goods exist only through the ledger). Raw goods a trader buys stay in its inventory and leave the economy when it leaves; coins it pays come from its purse (`purseCoins` 400, refilled every visit). `trade.credit.changed` carries the new credit.
- **Visits**: trader kinds are the prototypes with a `Trader` component. The schedule `visits[]` in `systems.trade`: first arrival `traderVisitStartDay` (3) x 288 + `nextInt(0, traderVisitJitterTicks = 72)` from the stream **`trade.visit`**; after a caravan is gone the next one is `traderVisitIntervalDays` (6) x 288 + jitter later; a hostile faction (standing either way below `hostileStanding` -30) or a missing market postpones by a day. The caravan enters at one of the reachable cells whose path cost to the market is at least 90 % of the largest (chosen with the same stream), walks to the first job board's cell (market), is `Present` for `traderStayDays` (2) days (`trader.arrived` when it arrives), walks back and is deleted (`trader.left` from the before-delete hook). A walk that fails sets it down at its goal. Traders are **not citizens**: no `Citizen`, `Needs` or AI components, so population, status lists and the settler systems never see them; the faction link is `Trader.factionId` (the content faction `merchant_caravans`, new `FactionType.Mercantile`). Their inventories are not counted as settlement stock (`materialStock`, the storage test helper).
- **Orders (the player's interface)**: `TradeSell {traderId, materialId, quantity}` and `TradeBuy` create a `TradeOrder` keyed by the trader *kind* (it outlives the visit). Checks: the entity is a present trader (`UnknownTrader`, `TraderAbsent`), a sale needs a trader that buys the material (`NotWanted`), a purchase one that sells it (`NotSold`) and enough stock or credit (`InsufficientStock`, `RefinedCreditExhausted`). The slot-10 pass posts one `trade.sell` / `trade.buy` job (system posting on the nearest running board, wage 1, priority 55, skill `trading`) while the trader is present and there is stock (sell: unreserved stock in storage) or coins and trader stock (buy). A sell trip: take what the settler carries or reserve the nearest stock, walk there, walk to the trader, negotiate, hand the coins into the treasury, book the trip. A buy trip: the settler takes the price of as many units as the order, the trader, its own inventory and the treasury allow, walks to the trader, negotiates (it may pay the coins it carries), hands the leftover back, and a `haul.deliver` job brings the goods to storage; a failed or interrupted trip returns the coins. Trips that only lose a stock race do not count as failures; three real failures cancel the order (`too_many_failures`). Orders and the last 16 finished ones are in `systems.trade.orders`; events `trade.order.created / completed / cancelled`; a refused `TradeSell` / `TradeBuy` queues `trade.order.refused {direction, traderId, materialId, quantity, kind, message}` before the command is rejected (`command.rejected` only carries the code `command-failed`).
- **Commands** (queued): `SetSellsItems {entityId, value}`, `SetPriceMultiplier {entityId, multiplierMilli}` (both add the `Merchant` component), `ProposeTrade {buyerId, sellerId, requested: Item[], offeredItems?: Item[], offeredCoins?}`, `WithdrawTradeOffer {offerId}`, `AcceptTradeCounter {offerId}`, `TradeSell`, `TradeBuy`, `CancelTradeOrder {orderId}`. **Queries**: `traders`, `trade-offers`, `trade-orders`, `trade-ledger`, `treasury`, `trade-quote {traderId, direction: Sell|Buy, materialId, quantity?}`. **CLI**: `traders`, `trade sell|buy <trader> <material> <qty>`, `trade orders|offers|quote|cancel`, `treasury`, `ledger`. **Events added**: `trade.order.*`, `trader.arrived`, `trader.left`, `treasury.rent.received`, plus the D-12 list.
- **Content added**: skill `trading`, trait `greedy` (margin_add +0.05), job types `trade.sell` / `trade.buy`, faction `merchant_caravans`, prototype `trader_caravan` (sells nails 60, coal 20, iron_hammer 2; buys iron_ore, limestone, oak_log, wheat; refines iron_ore -> iron_ingot at 500), constants `startingTreasury`, `traderVisitStartDay`, `traderVisitIntervalDays`, `traderVisitJitterTicks`, `traderStayDays`, `maxNegotiationRounds`, `offerTimeoutTicks`, `defaultMinimumMarginRate`, `agreementDiscount`, `scarcityMaxPremium`, `tradeStandingPerTrade` (1), `tradeStandingDailyCap` (5), `hostileStanding` (-30).
- **Side effects on existing content and tests**: the new trait changes the trait draws of the seed-42 settlers, so `scenarios/checkpoint-c.json` (and `docs/PLAYING.md`) give the mill and oven 200 more ticks (`step 700` instead of 500, the end state at tick 2880 is the same); `materialStock` and the storage test world ignore traders; content/query/command count tests grew.
- **Hamlet reachability (D-13/D-16, 027 validator input)**: with the existing `mine.ore` job (Hamlet) a Hamlet mines ore, sells it (`trade sell`), and buys exactly `floor(ore x 0.5)` iron ingots (`trade buy`) from the next visit; `scenarios/trade-ore-for-iron.json` plays it with player commands only. Orders are kept per trader kind, so the player may sell on one visit and buy on a later one.

### D-56 Diplomacy, NPC factions and envoys (task 4.2; `src/game/diplomacy`, `src/game/factions`)
- **Scope and descopes**: spec 021 as far as the player and the AI can use it; envoys fail only by timeout (D-14), the trade-policy screen stays descoped. The catalogue command `IssueDiplomaticAct` is the one command that sends gifts, trade agreements, declarations and overtures; the CLI verbs `gift`, `envoy` and `directives` only build it. `RespondToProposal` `counter` closes the proposal without a standing change (a counter-offer is a new act); `terms` is accepted and ignored (an agreement has the fixed terms of D-12, the 0.9 multiplier). Added: `CancelDiplomaticDirective {envoyId}` (the cancel of the pending list; refunds the gift).
- **Attitude (the derived "disposition" of a standing, never stored)**: `Hostile` below `hostileStanding` (-30), `Wary` below 0, `Neutral` below `friendlyStanding` (20), `Friendly` below `alliedStanding` (70), `Allied`. `isHostilePair(a, b)` (either view hostile) is the one hostile status: the trade gate (`faction-hostile`, trader visits postponed) and, through the mean standing of a worker's factions (the poster's own members always pass), the labour gate read it. `setStanding` queues `diplomacy.attitude.changed` on a band change besides `diplomacy.standing.changed`.
- **Deltas (content constants, steady values)**: a gift raises the receiver's view by `min(giftMaxDelta 25, giftBaseDelta 5 + floor(valueCoins / giftCoinsPerPoint 20))` and the giver's by `floor(delta / 2)`; the value is coins plus goods at `valueMilli`; an accepted trade agreement is `+agreementAcceptedDelta` (10) both ways with the flag on both lists; an accepted overture `+overtureAcceptedDelta` (5) both ways; a refused overture lowers the refuser's view of the sender by `rejectionPenalty` (3); a refused trade agreement changes nothing; war sets both views to `min(current, warStanding -60)` and ends the agreement (`diplomacy.agreement.cancelled`); peace sets both to `max(current, peaceStanding -10)`; neutrality sets both to 0. Acceptance is deterministic (no stream): an agreement iff the target's standing toward the sender is at least `agreementMinStanding` (20) and neither side is hostile; an overture iff at least `overtureMinStanding` (-15). The player's `RespondToProposal`: accept applies the acceptance deltas, reject lowers the settlement's view of the proposer by `rejectionPenalty`. Negative deltas that an NPC faction applies toward the government are `trunc(delta x factionHostilityMultiplier / 1000)` (peaceful 0.25, steady 1, harsh 1.5; the multiplier is read from the game options at every init and not saved).
- **Decay**: on the first tick of every `standingDecayIntervalDays` (2) day each non-zero standing value of every faction moves one point toward 0 (agreement flags are untouched). D-14 named no decay; 027 lists decay among the difficulty knobs, which here only scale hostility.
- **NPC factions** (records of `factions.json` with an `npc` block: `side`, `standingTowardSettlement`, `settlementStandingToward`, `overtureWeight`, `agreementWeight`, `incidentWeight`, `warLike`): seeded by `spawnNpcFactions` after the world generator, only when a map exists. Each gets the faction entity (`faction` prototype), `Faction.seat` (new field, `{mapId, cellIndex}|null`) = the extreme cell of the map edge on its `side` (ties lowest index; seats are abstract, nobody walks), two members of prototype `npc_leader` (a `Citizen` with `Identity`, `Skills` and `Inventory`, no `Position`, `Needs` or `TaskQueue`, so never a settler: population, status subjects and jobs ignore them; named by `assignIdentity`, which now also names non-humanoid entities that carry `Identity`) and the leader chosen by `pickLeaderCandidate`. The pack: `merchant_caravans` (east, neutral, the faction of the trader caravans), `ashford_barony` (north, wary -5 both ways, aggressive, war-like, makes insults), `wulfric_abbey` (west, friendly 25 / 20, pious). New `FactionType.Political`. The government's seat is the market cell (the first job board; there is no Throne Room yet).
- **Envoys**: prototype `diplomatic_envoy` (`Envoy` component and an 8-slot cargo inventory, no position). `dispatchAct` validates (both factions exist and differ, both seats on one map, the target has a leader, a trade agreement not to a hostile faction nor when one stands, a gift only from the settlement and only coins and goods that the treasury inventory holds, at most `maxEnvoysPerFaction` (4) envoys of the sender under way), moves the gift into the envoy, spawns it and queues `act.initiated` and `dispatch.started`. The trip takes `ceil(distance of the seat centres / envoyUnitsPerTick (100))` plus a jitter `nextInt(0, envoyJitterTicks 12)` on the stream `diplomacy.resolve`; `deadlineTick` is the dispatch plus `envoyStuckTimeoutTicks` (576). Slot 11: at `arriveTick` the message goes to the target's **current** leader (retargeting is implicit; a faction without a leader makes the envoy wait), the act is resolved at once and the envoy is removed `travelTicks` later (status `Delivered`); at the deadline the trip fails: `unreachable` while still on the way, `leader-unavailable` at a leaderless faction or when a faction was destroyed. The cargo of a failed or cancelled gift returns to the treasury at once (a `loose_pile` on the market cell when the treasury cannot take it). An envoy entity deleted from outside while traveling fails `envoy-destroyed` and refunds (before-delete hook). An overture or trade agreement from an NPC faction to the government becomes a **proposal** (`diplomacy.proposal.received`, saved in `systems.diplomacy`, lapses after `proposalExpiryTicks` 576 with `diplomacy.proposal.expired`); gifts and declarations apply at once. NPC envoys carry no cargo (NPC gifts are not built).
- **NPC AI** (stream `diplomacy.ai`): evaluates when `tick mod npcEvalIntervalTicks (72) == factionId mod 72`, the last act is `npcActCooldownTicks` (288) old and it has a leader. A `warLike` faction at standing -20 or worse (above `warThreshold` -50) declares war with chance `warChance` (10 %) x the multiplier; otherwise one of {overture (standing in [-15, 20), nothing of its own under way), agreement (standing 20 or more, none stands, nothing under way), incident (standing below 20)} is drawn by weight (the incident weight x the multiplier); an incident passes a chance gate `incidentChance` (20 %) x the multiplier and is an **insult**: the settlement's view falls by `incidentStandingDelta` (-5, scaled), the faction's own view by `incidentReciprocalDelta` (-2, scaled). There is no combat, raiding or hostile entity (D-14). Cooldowns persist in `systems.diplomacy`.
- **Succession** (every tick, slot 11, after the trader visits): a faction with `leaderId == null` picks `pickLeaderCandidate`; an NPC faction without members first gets a new `npc_leader`, the player's government without members stays leaderless. `SetFactionLeader {factionId, entityId|null}` lives in the factions system (errors `NotMember`, `UnknownFaction`). The styled name shows the office from `Faction.leaderId`, so no title event is needed.
- **Queries**: `factions-diplomacy` (every faction but the government: both standings and bands, `hostile`, agreement, leader, seat, `travelTicks`, envoys under way), `directives` (the settlement's envoys: act, target, status, ETA, deadline, cargo, failure), `envoys` (all), `agreements`, `proposals`. **CLI**: `diplomacy`, `gift`, `envoy [cancel]`, `directives`, `agreements`, `proposals`, `respond`, `leader`. Scenario: `scenarios/diplomacy.json` (player commands only).
- **Side effects on existing code and tests**: the NPC entities (3 factions, 6 members) and the envoys they send shift the entity ids of everything spawned later (tests and scenarios that name ids were renumbered: zones and sites from #10 to #19, the trader ids of `trade-ore-for-iron.json`); the status context's `citizens()` also requires `TaskQueue` (the NPC leaders are citizens without one); `Faction` gained `seat`; `isFactionHostile` and the labour gate use the attitude bands; the global vitest `testTimeout` went from 30 s to 60 s (the scenario determinism tests play a 3000-tick game twice, which came within seconds of the old limit under coverage on a loaded machine; the diplomacy pass itself costs about 3 microseconds per tick).

### D-58 Dwellings and household upgrades (task 4.5; `src/game/housing`)
- **Scope**: spec 029 as far as the pack and the player reach it: the `Dwelling` state on `dwelling` zones, the seven-step daily evaluation, requirements and streaks, supplied goods with the accumulator model, the household fetch chore, rent into the treasury, settlers arriving, the Dwelling status subject, queries, CLI verbs and the Hamlet to Village scenario. There are **no housing commands**: a dwelling is a zone, designated with `DesignateZone` (the catalogue has none for housing).
- **State**: `Dwelling {level, upgradeStreak, downgradeStreak, consumptionAccumulators, foodRecord, lastEvaluatedDay}` is added to a `dwelling` zone entity by `zone.requirements.met` (`ensureDwelling`; the daily evaluation repeats it as a safety net, so a save from before 4.5 gets it too). `Citizen.homeDwellingId` / `homeAssignedTick` already existed. Nothing else is saved: the status cache of `HousingService` is derived and empty after a load; the stream `housing.immigration` is a named PRNG stream and is saved with the others.
- **Evaluation (slot 13, `tickOfDay == housingEvaluationTickOfDay` = 72, D-28 order)**: 1 clear invalid homes (dead, not in the government, not a `Citizen` with a task queue, dwelling without `Dwelling`; a dwelling only flagged for deletion still counts so that its zone event decides), 2 supplied goods for active dwellings with residents (and the food record is pruned to the window), 3 requirements, streaks and at most one level change, 4 capacity (`min(level capacity, beds)`, latest `homeAssignedTick` first, ties higher id, `CapacityReduced`), 5 rent, 6 the homeless by ascending id into the highest-level dwelling with room (ties lowest zone id), 7 settlers. Rent comes before housing, so a household pays from the day after it was formed. The tier check of slot 15 runs on the next day boundary, so Village comes one day after the fourth dwelling and the second settler (D-16). The Steward (4.3, slot 14) does not exist yet; housing precedes it by pipeline order.
- **Streaks** (`advanceStreaks`, pure): the upgrade streak counts days on which every requirement of the next level holds (a tier-locked next level never does: `LockedByTier`), the downgrade streak days on which a current-level requirement fails; an upgrade wins over a downgrade of the same day; a Hovel keeps no downgrade streak; `housing.dwelling.at-risk` when the streak becomes 1. Inactive or uninhabited dwellings keep their streaks.
- **Supplied goods** (`supplyOutcome`, pure): accumulators are keyed by group signature (D-28). Spec 029 FR-009 says an unmet day caps the accumulator "at `1000 x units`"; taken literally the debt grows every day (the next day's `needed` includes the whole kept debt), which contradicts "demand does not pile up beyond one day". Decision: when the stock is short, nothing is consumed and the whole units that stay owed are capped at one day's worth (`ceil(daily demand / 1000)` units); the fraction of a unit is kept. A dwelling's daily demand uses the rates of the union of its current and next level (the higher rate when both name the group), also when the requirement status of another level is shown. Without storage furniture every group fails (`NoHouseholdStorage`) and nothing is consumed.
- **Services**: `ServiceNearby` uses one multi-source Dijkstra from the dwelling's tiles over the map's integer move costs (`multiSourceCosts`), no tie-breaking; the content field is still called `maxPathCells` (the D-28 rename to `maxPathCost` was not applied to the schema, the number is a path cost). The shipped pack has no services, so nothing in the pack uses it yet.
- **Household reservation (FR-017)**: storage furniture on dwelling tiles is left out of `listStorage` (so `stock`, routing and the queries of everybody else) and offered only to its residents (`listStorageFor`, `findSources(..., includeHousehold)`); beds on dwelling tiles are usable only by residents, who prefer them (`AiService.setBedPolicy`: rank 0 own, 1 other beds, `null` forbidden). **Bug fixed on the way**: `planNeed` looked for beds by entity prototype, but built furniture is a `furniture_piece` carrying `Furniture.furnitureId` (D-50), so no built bed was ever found and everybody slept on the ground; it now matches both.
- **Fetch chore (FR-016)**: the behavior nodes `household_needs_goods` / `fetch_household_goods` sit in `basic_needs` between the critical-need branch and `claim_job`; the action refuses while the settler holds a task at job priority or above; it enqueues `housing.fetch` at job priority 50 (so claiming waits until the chore is done). The household wants `householdStockDays` days of demand; the shortfall is taken from the nearest accessible storage outside the household, one source per trip, into the dwelling's storage furniture; at most one resident of a household fetches at a time; nothing is posted on a board. Deviation: no reservation is held while walking (the storage system releases `Haul` reservations of citizens without a haul task); the goods are taken on arrival, all or nothing, honouring other reservations, and the task remembers how many units it took so the settler's own goods of the same material are never delivered. No source: no task starts and the dwelling reports `MissingInput {materialId, required, available: 0, noProducer}`.
- **Rent (FR-013)**: coins are debited from the residents (one per resident per round, ascending id) and credited to the treasury by the trade system's `receiveRent`; if it refuses, the residents get them back (`TreasuryUnavailable`). The treasury is the government faction's inventory (D-55), so a missing throne room does not stop rent. Hovel rent is 0 in the pack (no events), Cottage 1.
- **Settlers (FR-015, D-17)**: `min(free slots, maxImmigrantsPerDay)` after the homeless are housed; the prototype is drawn from the dwelling level's weighted table on `housing.immigration`; a settler is spawned like a founder (traits, government, `assignIdentity`) on the arrival cell (the border cell of the throne room's map with the cheapest path cost to the lowest active throne room, ties lowest cell index; recomputed every evaluation), gets its home at once (`homeAssignedTick` is the spawn tick) and an idle-priority `move` to the dwelling. `housing.immigrant.arrived` is queued; no moment is recorded before 4.6 and `Arrived` stays Minor. Without a throne room or an arrival cell, `housing.immigration.blocked {reason}` is queued when settlers would have come.
- **Zone events**: a split keeps the level on both parts and resets streaks (residents beyond the parent's remaining capacity: `DwellingChanged`); a merge takes the lower level (the absorbed level comes from a before-delete hook, `HousingService.retire`), resets streaks and keeps residents by assignment tick up to capacity; a deleted dwelling evicts everybody with `DwellingRemoved`. The tier hook is installed with `setDwellingCounter`: active dwellings at or above a level.
- **Status (FR-019a)**: the `StatusSubjectKind.Dwelling` provider: inactive = Blocked `ZoneInactive {zoneId}` (cause: the zone, next to the zone's own `ZoneRequirementsUnmet`, D-18); no residents = Active; current level unmet = Blocked `DwellingRequirementsUnmet {targetLevel, unmet}`; only the next level unmet = Idle (`LockedByTier {requiredTier}` for a tier lock); `NoHouseholdStorage`; `MissingInput`. It reports the findings of the last evaluation and derives them itself after a load.
- **Queries and CLI**: `dwellings`, `dwelling {id}` (level, capacity, residents, rent, both streaks and grace days, the requirement checklist of the current and the next level, foods, accumulators), `housing` (totals, active dwellings per level, `immigrationBlocked`) and `dwellings-at-or-above {level}` (the spec's `countDwellingsAtOrAbove`); verbs `homes` and `home <id>`.
- **Balance for the Hamlet to Village path** (the v0 numbers are provisional, like D-54; measured with `scenarios/hamlet-to-village.json`): with six settlers the walls were the whole bottleneck (every quarry trip walks to a far deposit; a wall cost 2 blocks = 4 limestone, and the throne room and four rooms need 34 walls). **A wall costs 1 stone block** (was 2; the deconstruction yield stays 1) and **`quarry.stone` yields 4 limestone** (was 2). With the old numbers the same script had no dwelling by day 32; with the new ones the settlement is a Village at tick 9216 (day 32). The wall tests of the construction and status suites, `tier-progress.json` (the throne room is now active about day 7, so its `first-master-craftsman` assertions were dropped) and the content tests (two new behavior handlers) were adjusted.
- **Scenario `scenarios/hamlet-to-village.json`** (player commands only): the Checkpoint C opening plus a sawmill; on day 3 the food orders (priority 60, finite quantities), 24 saw crafts (priority 38) and 40 nails bought from the trader (`TradeBuy`); on day 5 the throne room, 60 stone blocks (priority 36) and four 2x2 dwellings, each with a door and two beds, their cells chosen by a layout search over the map (rings of eight to ten cells, shared walls, none on forest). Priorities follow the supply chain: food first, then building (46 down to 43 so the rooms finish one after the other), then planks, then stone; a downstream job with a higher priority than the supply that feeds it starves the supply. The founders are housed as the rooms finish, the two settlers arrive on day 31 and the settlement is promoted on day 32. The **first-dwelling-upgrade** milestone is not on this path (a Cottage needs the Village tier, six tiles, two foods eaten and bread in the household's storage; the pack has one food); tests with patched levels cover the upgrade.

### D-59 Standing orders and the Steward (task 4.3; `src/game/standing`)
- **Scope**: spec 026 as far as the pack reaches it: orders (settlement and zone scope), the hysteresis review, owned runs, the Steward and his audience, Notice Post and Bell Tower delivery, the status provider, queries, CLI and a scenario. Defaults are the D-19 numbers, now also in `content-constants.json` (which had placeholders 3 / 20 / 0.5 / 20 / `[96, 240]` / 24): `maxOpenRunsPerOrder` 5, `maxStandingOrders` 50, `defaultRestockFraction` 0.75, `noticePostRadius` 12 hops, `bellRadius` 25 hops, `stewardAudienceTicks` 12, `bellRingTicksOfDay` `[72, 108, 144, 180, 216]`, `stewardReviewTickOfDay` 72.
- **Pipeline order at tick of day 72**: housing (slot 13) runs first, then the Steward (slot 14), so the review counts the stock after the households took their goods (D-19, D-58, the pipeline table); the task text that said "Steward before housing" is superseded by the table. A test pins both slots.
- **A run is a production order**: the Steward's run is one craft. It is queued as a pending board update of origin `Steward` with the new change kind `Run {runId}` (`BoardChangeKind.Run`) on the board of the order, so it waits for a Town Crier like a player's posting; the crier's delivery (`applyBoardUpdate`) hands it to the applier the standing system installs with `CrierService.setRunApplier` and the applier calls `createProductionOrder` (recipe, quantity 1, the order's priority; the workstation with the fewest unfinished orders). The production poster then puts the `craft.produce` posting on the nearest board as for any order (D-53, systems post at once), so the order's board decides where the **crier** goes, not where the craft is posted. If no workstation can make the recipe on delivery, the run is dropped and the update abandoned (`change_rejected`); the next review tries again and the order shows `MissingWorkstation`. `deliverToZoneId` is not a posting field: a restocking zone-scoped order steers its material into its zone through `StorageService.setZonePreference` (routing tier 0, every other route stays the fallback, FR-020).
- **Run status is derived** (`PendingAdd`: the update is still queued or on a crier; `Claimed`: a craft of the order runs or its posting is claimed; `Open` otherwise); only `runId`, `orderId`, `boardId`, `updateId`, `productionOrderId` are saved. Withdrawing a pending add abandons its update (nothing is applied), withdrawing an open run cancels its production order; claimed runs are never withdrawn. Runs vanish when the production order ends, the update is abandoned or the order is gone (`pruneRuns`, every tick).
- **Hop distance versus path cost (D-19 resolved)**: the board of an order is chosen by **path cost** from the lowest cell of the throne room (own board, then the Steward's board, then the user-managed board with the cheapest reachable walk, ties lowest id); the reach of a Notice Post and of the bell is **hops** on the cell adjacency graph (`hopDistance`, breadth first, terrain and walls ignored). A Notice Post that has no walkable connection to the board is passed over, so the crier goes to the board itself.
- **Delivery hooks in the crier folder**: `CrierService.setRouter` (board to the Notice Post that serves it, `via: NoticePost`), `setRunApplier`, `setExclusion` (the Steward cannot be appointed crier; the Steward cannot be a crier). Dispatch groups waiting updates by destination, so one trip serves every board of a post; the deliver task's `boardId` is the destination (board or post) and the whole load is applied on arrival; a post that vanished on the way hands the updates back to the queue. The bell (slot 14) applies every pending update (waiting or carried) whose board is within `bellRadius` hops of the church bell with `via: BellTower`; a crier left empty is released by `recoverCriers` (it does not walk back to the throne room: deviation). Content added: furniture `notice_post` (village), `church_bell` (market_town), zone type `bell_tower` (no room, one church bell, market_town); the bell is out of reach in v0 (no ingots before the Market Town).
- **Counting (FR-006)**: storage furniture of the settlement (household storage and loose piles left out), plus for the settlement scope the unreserved units in workstation inventories and what citizens running `haul.deliver` carry; a zone scope counts the furniture on the zone's tiles only. Goods still being crafted are not stock, so the number of owned runs (claimed ones included) is what bounds the overshoot.
- **Review**: at `stewardReviewTickOfDay` or after `RequestStewardReview` (the request is spent by the next pass of slot 14, so it runs on the tick the command is applied; repeats collapse). Needs a Steward and an active throne room, else `steward.review.skipped {NoSteward | NoSeatOfGovernment}` and the runs stay. The review gives the Steward the task `govern.steward_audience` (priority 70, walk to the throne room, stay 12 ticks; none is queued twice). Paused orders, orders whose zone is gone only withdraw their unclaimed runs, orders whose recipe is locked do nothing. Orders are evaluated by priority (highest first) then id.
- **Reasons (FR-025)**: `Paused` alone for a paused order, else `NoSeatOfGovernment`, `NoSteward`, `LockedByTier`, `ScopeZoneMissing`, `NoReachableJobBoard`, `AwaitingTownCrier` and, while the order restocks or owns runs, what production reports for its open runs or its recipe (`MissingInput`, `MissingWorkstation`, `NoQualifiedWorker`, `MissingRoom`, ...); a missing input that another standing order makes carries that order as `causeRef` (so `why` follows bread to flour). The state is derived as D-19 says. The test status world swaps the real provider for its synthetic `StandingOrder` subjects with the new `StatusService.replaceProvider`.
- **Commands and errors**: the catalogue names (`UpdateStandingOrder`, the CLI verb is `standing edit`); errors are `StandingOrderError` whose message starts with the kind (`NoProducingRecipe`, `AmbiguousRecipe` with `candidates`, `InvalidQuantity`, `DuplicateOrder` (one live order per material and scope), `UnknownZone`, `UnknownOrder`, `BoardNotUserManaged`, `IneligibleSteward`, `TooManyOrders`, `ContentLocked`, `UnknownMaterial`, `UnknownRecipe`). A deleted order stops counting towards the cap and the duplicate rule, its unclaimed runs are withdrawn at once and the record is dropped with its last run. ### D-60 Chronicle and journals (task 4.6; `src/game/chronicle`)
- **Scope**: spec 028 from the moment sources on: every kind of `NotableMomentKind` is recorded once per triggering event into the citizen's journal and, when Major, into the settlement chronicle; the finest table; `Died` with the last styled name; `RenameCitizen`; the queries `chronicle {entityId?, kind?, limit?}` (newest first), `journal {entityId}` and `moments-since {tick}`; the verbs `chronicle [n] [citizen <id> | kind <kind>]` and `journal <id>`; `inspect` shows the last three journal lines; the scenario `scenarios/chronicle.json`.
- **Levels (D-17)**: `Arrived` is Minor. Major: `MasteryAchieved, BecameFinest, TookOffice, Died, SettlementMilestone, TierReached`; the other ten kinds are Minor (journal only). The enum has two prominences (`minor`, `major`); there is no third "Notable" level. The prominence is fixed per kind and checked by the save schema.
- **Records and params**: `MomentRecord {momentId, tick, kind, prominence, entityId|null, nameSnapshot|null, params}`; params are strings and integers, typed per kind in `chronicleTypes.ts` (TitleEarned `{skillId, noun}`, MasteryAchieved `{skillId, noun, guildId}`, BecameFinest / LostFinest `{skillId, noun, level}`, JoinedGuild / LeftGuild `{factionId, guildName}`, TookOffice / LostOffice `{factionId, office}`, FirstWork `{skillId}`, FirstTrade `{partnerId}`, HomeImproved `{dwellingId, dwellingLevel}`, Renamed `{previousName}`, Died `{journalExcerpt}`, SettlementMilestone `{milestone}`, TierReached `{tier, previousTier}`, Arrived `{}`). The id comes from the root counter `nextMomentId` and is mirrored into `SettlementChronicle.nextMomentId`. The event `chronicle.moment.recorded` carries the whole record (the catalogue payload).
- **Text**: never stored. `formatMoment` renders the content template of the kind; `{name}` is the snapshot, `{settlementNoun}` is the noun of the tier the record names (`tier`) or else the tier in force **at the record's tick** (`tierAtTick` from `tierReachedAtTick`), so a hamlet-day moment keeps saying "hamlet" after the promotion. The templates for `renamed`, `settlement_milestone` and `home_improved` gained `{previousName}`, `{milestone}` and `{dwellingLevel}`.
- **Journal**: `Identity.journal`, oldest first, `journalCapacity` 16 (content constant, was 20 in the pack; D-17 says 16); when full the oldest entry other than `Arrived` is dropped. `Identity.seenSkills` (sorted) keeps `FirstWork` once per skill and `Identity.tradeSeen` keeps `FirstTrade` once per citizen, both independent of the journal (a trimmed entry is never recorded again). Journals of non-members stay empty; a skill seen before a citizen joined is not remembered.
- **Chronicle**: `SettlementChronicle.moments` holds the Major moments in recording order, `chronicleCapacity` 200 (was 100 in the pack), the oldest dropped first. Only Major moments enter it, so there is no pinning rule to apply (`Arrived` stays out). The query returns it newest first (FR-024's view); the record order is ascending by id.
- **Size budget (SC-006, D-17)**: 1 MB for 200 full journals plus a full chronicle. A test builds the worst case it can (200 citizens, 16 entries each with a six-digit dwelling id and a long dwelling level, 200 mastery moments with long skill ids) and measures about 650 KB of serialized `Identity` and `SettlementChronicle` data. No further compaction was needed; the fix was the capacity of 16 and the single shared record shape.
- **Members only**: a moment about a citizen needs a named member of the player government. Visitors and NPC leaders (named at spawn) get none; `SettlementMilestone` / `TierReached` have no citizen. `Arrived` is recorded when the citizen joins the government (founders at tick 0 included), after the name re-check (D-17): a name that now collides with a living member (same full name and ordinal) gets the lowest free ordinal `>= 2`, no redraw, and `identity.named` is queued.
- **Sources**: `faction.membership.changed` (Arrived; JoinedGuild / LeftGuild only for occupational factions), `identity.title.changed` (Mastery for Master; TitleEarned when the new title is a Practitioner one after no title or another Practitioner title), `skill.increased` (finest table), `skill.work.completed`, `trade.completed` (both parties), `faction.leader.changed` (TookOffice for the new, LostOffice for the old leader, `office` = the faction's `leaderTitle`, `leader` when empty), `steward.appointed` / `steward.dismissed` (TookOffice / LostOffice with `office` = `stewardTitle`; a Steward who died gets no LostOffice), `housing.dwelling.upgraded` (one HomeImproved per resident of the dwelling at the time, `dwellingLevel` = `toLevel`), `settlement.milestone.reached`, `settlement.tier.reached`.
- **Finest (FR-015)**: per skill one entry `{entityId, level, sinceTick, lastAnnouncedTick}`, sorted by skill id. A member at or above `finestMinimumLevel` (40 in the pack) who strictly exceeds the holder takes over; the holder's own growth updates the level; ties change nothing. BecameFinest (Major) and LostFinest (Minor, previous holder, its last level) are recorded only when `finestCooldownDays` (3) passed since `lastAnnouncedTick`, else the change is silent. A skill without an entry first looks for a member who already leads (a settler who started skilled): that member is entered silently with `lastAnnouncedTick` 0, and a tie does not displace it. When the holder dies or leaves the government the entry is re-elected by scan (highest level, ties lowest id, at least the minimum) without moments, or dropped.
- **Died**: recorded by a before-delete hook (`registerDeathHook`) registered right after the identity hook and before the factions hook, so the moment is made while the citizen still has its Identity, its offices and its membership. It carries the same styled name that `entity.deleted` carries (offices included) and `journalExcerpt` (kinds of the last four journal entries, `kind:skillId` for those with a skill); the journal itself dies with the citizen. This differs from the task text only in where the moment is recorded: a handler on `entity.deleted` cannot tell a settlement member from an NPC leader any more, because the membership is gone with the entity.
- **Steward office in names**: `officesOf` appends `{government, "Steward"}` (`stewardTitle`) for the citizen who is `stewardEntityId`, after the faction offices: `Godiva the Farmer, Steward of the Settlement`. The old name snapshots keep their text.
- **Rename**: `RenameCitizen {entityId, givenName, byname|null}` (queued like every command; a failure shows as `command.rejected`) trims, accepts 1 to 40 characters (byname 0 to 40, empty means none), refuses control characters, applies the ordinal rule without a redraw, queues `identity.named` and records `Renamed {previousName}`; a rename to the current name changes nothing. Errors are `IdentityError` with the kinds `InvalidName` and `UnknownEntity` (the message starts with the kind).
- **Hash note**: the `Identity` component gained `journal` and `tradeSeen`, so every saved game differs from before; no scenario or test pins a literal state hash, nothing was re-recorded. Note that the state hash counts the command ids consumed by `save` and `load`, so a saved-and-loaded game is compared with an unsaved one through its records, not its hash.
- **SC-005 (at most 2 Major moments a game day)**: along `scenarios/hamlet-to-village.json` (32 days, 13 Major moments, mostly mastery and finest) and `scenarios/chronicle.json` (14 days, 11 Major) the average stays far below 2; `tests/integration/chronicle.test.ts` asserts the bound and that no day has more than 8.

## Task 5.3 part 2b animals and behavior trees (D-140 to D-145)

### D-140 Animals are entities without citizen components
- **Decision**: the 13 animal prototypes of spec 022 US11 (7 livestock, 6 wild; `animal-prototypes.json`) are entity prototypes with `Position`, a 4-slot `Inventory` (their products), `TaskQueue`, `AiState`, `Health` and the new `Animal` component `{prototypeId, kind, hungerMilli, nextProductTick, attackReadyTick}`. No `Citizen`, `Identity`, `Needs` or `Mood`: population, status, housing and the chronicle ignore them, the query `animals {kind?, prototypeId?}` (and the CLI verb `animals`) lists them, `entities` and `map` show them like any entity. The record gained optional fields (all defaulting to "none", so v0 records are unchanged): `dietTerrainIds`, `preyIds`, `productIntervalTicks`, `fleeRadiusCost`, `detectionRadiusCost`, `aggressive`; `products` are the periodic yields of a live animal (wool, milk, eggs), `drops` what butchering or hunting yields.
- **Numbers (the spec gives none)**: sheep 2 raw wool every 1152 ticks (4 days), cow 3 milk and goat 2 milk and chicken 2 eggs every 288 ticks (a day); radii in path cost (60 to 80 is 6 to 8 cells), hunger +0.1 percent a tick, a grazing animal loses 2 percent a tick on its diet terrain. Livestock drops: cow 8 meat, goat 1 hide and 3 meat, pig 6 meat and 2 tallow, and (deviation, the spec lists none, butchering them would be empty) sheep 3 meat and chicken 1 meat; horse and donkey have no drops. Wild drops follow the spec (deer 6 meat 2 hide, rabbit 1 meat, boar 5 meat 1 hide 1 tallow, wolf 1 hide, bear 10 meat 3 hide, fox 1 hide). Threat levels 0, 0, 2, 3, 4, 1 (none, none, medium, high, very high, low); wolf prey: livestock, rabbit, deer; fox prey: chicken; boar and bear are `aggressive`.
- **Spawning**: wild animals are placed at the end of the new-game init (a `fauna.tick` init that depends on diplomacy; `spawnFauna`) from the stream `world.fauna` only, so terrain, settlers, the chest and the NPC factions keep their ids and every existing draw is unchanged. One animal per 60 (threat 0), 120, 150, 250, 400 free habitat cells (at most 6, 2, 2, 2, 1), at least one for deer, rabbit and fox, none within six cell spacings of the village, never two on one cell. Seed 42 Small: 1 deer, 4 rabbits, 2 foxes (entities 19 to 25). **Entities created later get ids 7 higher** (zones, sites, traders): the hard-coded ids of the scenarios `hamlet-to-village`, `trade-ore-for-iron`, `zones` and `world-gen` and of three CLI verb tests moved by 7 (`#19` to `#26`, trader 50 to 57 and 59 to 66), the entity totals (18 to 25, 20 to 27, state view 20 to 27) and the ASCII golden of seed 42 (animal markers); nothing else in those scenarios changed. Fauna ids cannot come last or from another range: the store requires strictly ascending ids.

### D-141 The seven role trees and the animal trees
- **Decision**: `behavior-trees.json` holds 11 trees: `idle_wander` and `basic_needs` (v0), the 7 of spec 022 US14 and the two the cross-reference list asked for (item 8: deer, rabbit and fox had no tree): `prey_behavior` (deer, rabbit) and `fox_behavior`. Trees refer to each other with the existing `run_tree` action (D-15, no engine change): `daily_routine` = critical needs, household chore, `run_tree worker_cycle`, `run_tree idle_wander`; `worker_cycle` = `jobs_available` + `claim_job` (the job system's `claim_job` already walks, fetches and works, so the spec's `travel_to_worksite` / `gather_materials` / `perform_work` leaves are that one action); `guard_patrol`, `merchant_routine` and `priest_routine` put a role branch after the critical-needs branch and end in `run_tree daily_routine`. Depth is at most 5 (tested).
- **Handlers**: `zone_available` and `go_to_zone` (param `zoneTypes`, `market` for the merchant, `chapel,church,cloister` for the priest, which fail while no such zone is active so the entity falls through to the daily routine) and `hostile_animal_near` / `engage_threat` (a guard walks to a predator within about 8 cells and strikes it for a third of its health, no drops) in `src/game/roles`; the animal handlers in `src/game/fauna` (with `outside_pen` and `return_to_pen` for the pasture). The spec leaves not modelled, for lack of a system behind them: the social, comfort and faith branches of `daily_routine` (`seek_conversation`, `seek_comfort`, `attend_worship`), `guard.patrol` and `guard.watch` duty, merchant restock and the daytime test, the sermon and the charity trigger (listed in `docs/content-crossrefs-5.3.md`).
- **Order deviation**: in `livestock_behavior` and `prey_behavior` the flee branch comes first (the spec lists feed, graze, flee), because flee must win when a threat is near (spec scenario US14.5); `daily_routine` keeps the order of `basic_needs` (household chore before work), not the spec's order, so settlers behave as before.
- **Mapping**: the v0 four (`peasant`, `farmer`, `carpenter`, `baker`) keep `basic_needs`; the 19 others use `daily_routine`, guard and soldier `guard_patrol`, merchant `merchant_routine`, priest and monk `priest_routine`. `daily_routine` behaves like `basic_needs` (same order, same handlers), so immigrants and any later arrival of those prototypes act as v0 settlers do.

### D-142 Animal jobs
- **Decision**: three executors in `src/game/fauna/animalJobs.ts`, registered with `registerJobType`; the job content (`tend.animals`, `hunt.game`, `butcher.animal`) is the 5.3 part 2a content (their entries left `deferredJobReasons`; `tend.bees` stays deferred; the skills of the content, `combat` for hunting and `animal_husbandry` for butchering, only give work speed and experience). A posting names the animal in `target.entityId` (`PostJob` / `PostCustomJob` accept `entityId`); the cell is only where it was seen. The worker walks to the animal's current cell and, when the animal has moved on (it flees, it wanders), walks again, at most 12 legs (`lost_quarry`, released with a back-off); within about one cell (`contactCost` 25) it works 8 ticks (scaled by `workDuration`) and the effect applies. `tend.animals` takes everything a livestock animal holds (nothing held: `target_invalid`), `butcher.animal` (livestock) and `hunt.game` (wild) give the animal's drops plus what it held, as far as the worker's inventory has room, and remove the animal (`animal.died`, cause `butchered` / `hunted`). Wrong kind or an animal without drops is `target_invalid`; the posting's `outputs` of the content are not used for the real yield (the record's drops are).
- **Hunting works because of the flee model**: a fleeing animal runs at most 40 path cost (four cells) and freezes 8 ticks; settlers and animals have the same speed, so the hunter closes in during the freeze (tested with a deer, and in `scenarios/fauna.json`).
- **No auto-poster**: the player or a Steward posts these jobs; nothing posts them by itself (there is no pasture, no demand model for meat yet).

### D-143 Predators, thieves and the bear: combat-lite
- **Decision**: there is no combat system. A predator (threat level 2 or more: boar, wolf, bear) that sees prey of its record within detection range, with no guard in range, goes for it with the roll `predatorHuntChance` (250 per mille, stream `fauna.hunt`) per decision; within one cell an attack takes 25 percent of the prey's health (cooldown 12 ticks), prey at zero health is removed (`animal.died`, cause `predation`). The fox takes a chicken within reach at once (cause `stolen`, spec scenario 5). Aggressive animals (boar detection 20, bear 60, a boar only attacks when "cornered", i.e. very close) walk to a humanoid and hurt it for 8 percent of health per attack, never below 1 percent, so an attack cannot kill a settler. Non-aggressive predators and all prey flee from humanoids within their flee radius. Livestock flee from predators only. A guard strikes a predator for 34 percent of its health (`engage_threat`), the predator is removed at zero health without drops.
- **Rare by construction**: predators spawn only where their habitat is large, with at most 1 or 2 per species per world; seed 42 Small has none.

### D-144 AI hook: wake checks
- **Decision**: `AiService.registerWakeCheck(check)` and `shouldWake(engine, entity)`; `isDueForDecision` (slot 5) also returns true for an entity whose tasks are all below need priority when a wake check says so. The fauna system registers one (`animalWakesForThreat`): a busy animal without a flee task, whose flee radius contains a threat (humanoids for wild animals, predators for livestock), decides on its scan tick (`(tick + id) % 4 == 0`), so a stroll is interrupted by a threat within four ticks. Without a registered check nothing changes for settlers.

## React renderer shell and map canvas (plan 6.1 and 6.2, D-100 to D-109)

- **D-100 Renderer boundary and preferences**: `src/renderers/react` imports only `src/game/api` for values (eslint `no-restricted-imports` with type imports allowed, like the CLI); tests are exempt. Renderer preferences (autosave interval in ticks, toast burst limit, badge and zone toggles) live in `localStorage` through `prefs/rendererPrefs.ts`, never in a save; a missing or throwing storage means defaults. Terrain and zone colours are tables in `prefs/terrainColors.ts`.
- **D-101 The clock**: `EngineHost` owns the only timer, the engine's `AutoRunner` behind an injectable `Scheduler`, wrapped by the new `createSessionRunner(session, {scheduler, onTick})` in `src/game/api` (the renderer may not import `engine/`). Each scheduled tick is the ordinary `step(1)` command, so UI sessions are logged and replay to the same hash; a paused game keeps polling and only applies queued commands. The host notifies React once per tick (not per event) and skips a notification when neither the tick nor the pending-command count changed. Pause, resume and speed are the commands `pause`, `resume`, `set-speed`. A new game started from the new-game screen is paused afterwards so the player can look around first.
- **D-102 Store and hooks**: `GameStore` has a version number as state; every tick, command, step, new or loaded game bumps it. `useGameState(selector)`, `useQuery(name, args)` and `useEvents(pattern)` re-evaluate per version; each distinct query runs once per version (cached) and is shared. Map geometry uses `useStaticQuery` (per game epoch). Throttling is by tick, never by a real timer; toasts expire with game ticks.
- **D-103 Two read-only queries added to `src/game/api`**: `map-geometry {mapId}` (the cell polygons, a pure function of params and seed, never saved) and `map-entities {mapId}` (id, prototype, cell and component names of every entity with a Position on the map, so the renderer needs one query instead of one `entity` query per entity). Both backward compatible; typed methods `query.mapGeometry` and `query.mapEntities`.
- **D-104 Navigation and panels**: screens are an enum (`Screen`) routed by a `NavigationStore` (no URL router: a single page, no reload). `screens/screenRegistry.tsx` lists the screens; later tasks replace a `PlaceholderScreen` entry. `screens/sidePanels.ts` lists the panels docked beside the map; later tasks append theirs. Without a game only New game and Settings are enabled.
- **D-105 Selection and tools**: `SelectionStore` (active map, selected entity and cell, hover, camera focus requests with a nonce) and `ToolStore` (`Inspect`, `Place` with a prototype id) are the shared state between the map and panels. A click selects; opening the full inspection panel is task 6.3's decision. In `Place` mode a click on a cell that `validate-placement` accepts sends `PlaceFurniture`, `PlaceWall` or `PlaceDoor` (same mapping as the CLI `build` verb) and stays in the mode; a refused cell does nothing. Hard versus soft constraints are the engine's: the ghost is red exactly when `validate-placement` says not valid.
- **D-106 Picking without WebGL**: for an orthographic camera the ray through a pixel meets the ground plane at one analytic point (`screenToGround`), so picking is pure math (`cameraMath.ts`), unit-tested, and works identically for square and voronoi maps through a bucket-grid plus exact point-in-polygon `CellPicker`. Entities are picked by their cell (citizens, then furniture, then walls). The camera is an isometric orthographic one (pitch `atan(1/sqrt2)`): drag to pan, wheel to zoom about the pointer, rotate in 45 degree steps with Q and E or the buttons. Desktop only: no touch gestures.
- **D-107 Generated primitives and performance**: no external assets. Entities are merged boxes, cylinders, spheres and cones, one `InstancedMesh` per visual kind (citizen, trader, livestock, wall, door, build site, furniture, marker) plus crop plants; the terrain is one vertex-coloured mesh and one outline, the overlays are separate cell meshes. Entities and crops outside the visible ground are not laid out (culling). A 64x64 map with 4096 entities is tested through the three.js test renderer. World units: a square tile is one unit, a voronoi map is `sqrt(cellCount)` wide.
- **D-108 Testing the WebGL part**: `MapCanvas` is the only component that needs WebGL and is a pure function of `MapCanvasProps`; `AppServices.mapCanvas` lets jsdom tests substitute a stub, while the layers are tested with `@react-three/test-renderer`. The UI smoke test `runScenarioThroughHost` plays checkpoint-c's commands and steps through `EngineHost` and requires the same state hash as the CLI path, and the same hash when the fake-scheduler clock advances time.
- **D-109 Save and load in the browser**: the save is the engine's save text offered as a JSON file download (`kreuzvibe-day<N>-tick<T>.json`) and loaded from a file picker; the autosave slot is one `localStorage` entry written every `autosaveEveryTicks` ticks (default 288, one day; 0 turns it off); a full or blocked storage only loses the autosave. The trade-policy screen stays out (owner decision).
